A capstone exercise · Domain one

Build a coordinator,
two subagents,
and the safety net.

A fintech onboarding system that touches everything from Domain 1 — agentic loops, hub-and-spoke orchestration, explicit context passing, programmatic prerequisite gates, PostToolUse hooks, and structured human handoff. Try it before you reveal the solution.

The scenario

A fintech onboarding system.

You're building a customer onboarding agent for a fintech company. New customers can open an account, link external bank accounts via a third-party provider, and make their first deposit. Two backend systems are involved, and they don't agree on how to format their data.

Backend systems
  • Identity service — internal API (KYC/AML verification)
  • Bank linking service — third-party (returns timestamps as Unix epochs)
Compliance rules
  • Identity must be verified before any account creation
  • First deposits over $10,000 require human compliance review
  • Subagents should run efficiently — parallel where possible
Your task

Design the architecture.

Provide your design in pseudocode plus a brief architecture description. You don't need to write production-ready code — what's being evaluated is the architectural decision-making, not syntax.

  • 01
    A coordinator with two subagents

    An identity agent and a bank-linking agent. Hub-and-spoke pattern.

  • 02
    Proper context passing

    Explicit, structured prompts for each subagent — no inheritance assumed.

  • 03
    A programmatic prerequisite gate

    Preventing account creation before identity verification, and blocking high-value deposits.

  • 04
    A PostToolUse hook

    For data normalization across the heterogeneous timestamp formats.

Deliverables

Cover these six points specifically in your answer:

  • A Coordinator's allowedTools. What goes in it, and why.
  • B Identity agent's Task prompt. What does the coordinator put in it — content and metadata.
  • C Sequential or parallel? Whether the two subagents run in sequence or in parallel, and why.
  • D Prerequisite gate pseudocode. What tool calls does it intercept, what condition does it check.
  • E PostToolUse hook pseudocode. Which tool's output, what transformation.
  • F Escalation handoff for $15,000 deposit. What does the handoff to the human compliance reviewer contain.

!Traps a strong design avoids

  • Letting the bank-linking agent run before identity is verified
  • Passing context implicitly (assuming subagents inherit it)
  • Using prompts instead of hooks for the $10,000 threshold
  • Forgetting that the human compliance reviewer doesn't see the conversation
  • Treating the bank service's Unix epoch timestamps as the agent's problem to handle

Reference solution

One working design.

This isn't the only valid answer — but it hits every Domain 1 concept the exercise tests. Compare it against your own and note where your reasoning differs.

Architecture at a glance

A coordinator orchestrates two specialized subagents — identity verification first, then banking operations. Two safety mechanisms layer in: a pre-tool-use hook for compliance enforcement, and a PostToolUse hook for data normalization. The compliance threshold for first deposits is enforced programmatically, not by prompt.

A
Deliverable A
Coordinator's allowedTools
PSEUDOCODE
coordinator_allowed_tools = ["Task", "escalate_to_human"]
Reasoning
  • "Task" is mandatory — without it the coordinator literally cannot spawn subagents
  • "escalate_to_human" is needed for handing off compliance cases that exceed agent authority
  • Notably excluded: the actual backend tools (verify_identity, link_bank_account, etc.) — those belong to the subagents. The coordinator orchestrates; it doesn't execute backend operations directly.
Note: the subagents have their own restricted toolsets and notably do not have "Task". Preventing recursive subagent spawning is a deliberate architectural choice — it keeps budgets bounded and observability intact.
B
Deliverable B
Identity agent's Task prompt

Three slots: content, metadata, goal. Each one earns its place. Subagents have zero memory of the coordinator's conversation — every field that matters must be explicit.

PROMPT STRUCTURE
{ "goal": "Verify customer identity per KYC/AML. Return verification status and verified_customer_id.", "content": { "customer_provided_data": { "full_name": "Jane Smith", "date_of_birth": "1985-03-12", "ssn_last_4": "4421", "address": "123 Main St, Boston, MA" } }, "metadata": { "session_id": "onb-2025-04471", "request_timestamp": "2026-05-06T14:32:00Z", "regulatory_region": "US" }, "quality_criteria": "Return verification_status, verified_customer_id (if verified), confidence_score, failure_reason (if failed)." }
Why structured this way
  • Subagent has zero memory. Every field must be explicit.
  • Goal-based, not procedural. "Verify identity per KYC requirements" rather than "step 1: call verify_identity, step 2..." — lets the subagent adapt.
  • Metadata separated from content so the subagent can preserve provenance in its return.
  • Quality criteria specified so the coordinator gets back a structured response it can route on.
Trap avoided

Procedural prompts ("step 1: do X, step 2: do Y") lock subagents into fixed sequences that can't recover from edge cases. Goal-based prompts let the subagent figure out how; the coordinator just specifies what good output looks like.

C
Deliverable C
Sequential, not parallel

The two subagents run sequentially — identity first, banking second. This isn't a performance preference; it's a regulatory requirement.

EXECUTION FLOW
# Coordinator turn 1 emit [tool_use: Task(identity_agent, ...)] # wait for verified_customer_id # Coordinator turn 2 emit [tool_use: Task(banking_agent, customer_id=verified_id, ...)]
Why not parallel

Parallel execution requires independent subagents. Here, banking has a hard dependency: you cannot link bank accounts to an unverified customer. Running them in parallel would either fail (no customer_id available yet) or, worse, succeed in linking accounts that were never verified.

PatternWhen to use
Parallel Genuinely independent subagents (e.g., web search + internal docs + statistics — none depends on the others)
Sequential Dependencies between subagent outputs (e.g., banking depends on identity verification)
Trap avoided

Using parallel spawning just because the SDK supports it. Parallel is for genuinely independent work, not for performance optimization at any cost.

D
Deliverable D
Pre-tool-use hook · the prerequisite gate

Two gates in one hook: identity prerequisite, and deposit threshold. Both deterministic. No prompt instruction can override them.

PSEUDOCODE
def pre_tool_use_hook(tool_name, tool_args, conversation_history): # Gate 1: Account ops require verified identity if tool_name in ["create_account", "link_bank_account", "make_first_deposit"]: verified_id = extract_verified_customer_id( conversation_history ) if not verified_id: return BLOCK( message="Customer must be verified first. Call verify_identity." ) # Gate 2: First deposits over $10K need review if tool_name == "make_first_deposit": amount = tool_args.get("amount", 0) if amount > 10000: return BLOCK( message="Refunds over $10,000 require compliance review. Use escalate_to_human instead." ) return ALLOW
What it intercepts
  • create_account, link_bank_account, make_first_deposit — all checked against the prerequisite
  • make_first_deposit additionally checked against the $10,000 threshold
What it checks
  • Conversation state for a verified customer ID returned by an earlier verify_identity call. Not just any string the agent provides — the actual conversation history.
  • Tool arguments for the deposit amount.
The deterministic guarantee. The hook runs in your application code, not in the model. It cannot be talked out of — no prompt instruction can convince it to allow a violation. The block message guides the agent toward the correct workflow ("use escalate_to_human" instead).
E
Deliverable E
PostToolUse hook · timestamp normalization

The bank linking service returns Unix epochs. Internal services return ISO 8601. Without normalization, the agent compares 1730764800 against "2026-05-05T10:30:00Z" and produces wrong conclusions about event ordering.

PSEUDOCODE
def post_tool_use_hook(tool_name, raw_result): # Normalize timestamps from the bank service # to ISO 8601 before the agent sees them. if tool_name in ["link_bank_account", "get_linked_accounts", "fetch_account_balance"]: for field in ["linked_at", "last_updated", "verified_at"]: if field in raw_result: if is_unix_epoch(raw_result[field]): raw_result[field] = unix_to_iso( raw_result[field] ) return raw_result
Which tool's output

The bank linking service tools — link_bank_account, get_linked_accounts, fetch_account_balance. Internal services already return ISO 8601 and pass through unchanged.

What transformation

Unix epoch integers (e.g. 1730764800) → ISO 8601 strings (e.g. "2024-11-05T00:00:00Z").

Trap avoided

Putting timestamp conversion instructions in the system prompt. The model would get it right most of the time and fail occasionally. PostToolUse normalization makes it deterministic — the agent never knew there was an inconsistency.

Why hooks, not better tools? In production, you don't always own the tools. Third-party MCP servers return data in whatever format their backend uses. Backend systems are owned by other teams; coordinating format changes across teams is slow. The hook sits in your agent code — you control it, you can ship it today.
F
Deliverable F
Escalation handoff for the $15,000 deposit

The threshold gate blocks the deposit. The block message redirects the agent to escalate_to_human. The handoff payload looks like this:

HANDOFF PAYLOAD
{ "handoff_type": "compliance_review_required", "customer_id": "cust-verified-9924-A", "session_id": "onb-2025-04471", "conversation_summary": "New customer Jane Smith completed KYC verification successfully. Linked external bank account at Chase (ending 4471). Requested first deposit of $15,000.", "investigation_results": { "identity_verification": "verified | conf 0.97", "kyc_check": "passed | no flags", "linked_bank": "Chase ****4471", "deposit_amount_requested": 15000, "deposit_source": "verified linked account" }, "root_cause": "Deposit exceeds $10,000 threshold for automated processing of first deposits. Compliance review required per company policy.", "recommended_action": "Review source-of-funds documentation. If standard documentation can be provided, approve; otherwise request additional verification.", "reason_for_escalation": "Threshold exceeded — programmatic policy gate triggered. Not customer request, not agent capability limit.", "agent_actions_taken": [ "Verified identity via identity_agent", "Linked external bank via bank_link_agent", "Attempted first deposit | blocked by gate" ] }
Why every field earns its place

The compliance reviewer has no access to the conversation transcript. They cannot see the customer's messages, the agent's reasoning, or the tool calls that ran. Without this structured payload they would have to either contact the customer (frustrating them) or guess at the situation.

The six required fields, present
  • customer_id — verified ID for account lookup
  • conversation_summary — replaces the transcript the human can't see
  • investigation_results — what the agent found
  • root_cause — best understanding of why this is happening
  • recommended_action — what the agent thinks should be done
  • reason_for_escalation — policy gap, customer demand, or agent's capability limit

Plus an agent_actions_taken log so the reviewer knows what's already been done and doesn't repeat steps.

The handoff principle holds across boundaries. Whether the receiver is another Claude instance (subagent) or a human reviewer, the rule is identical: assume zero shared context. Compile and pass everything explicitly.
