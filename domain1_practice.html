1.1 Agentic loops 2 q
Q01 Task 1.1Loop control

Your agent calls lookup_order, gets the result, and then your code sends the next request to Claude. What MUST you include in that request for the model to reason correctly about the next step?

Model answer

The tool result, appended to conversation history as a tool_result block. Without that appended result, Claude has no idea what lookup_order returned and will either re-call the tool or hallucinate a response. stop_reason drives your code's control flow; the appended tool_result is what tells Claude what happened.

Q02 Task 1.1Termination signal

A teammate proposes: "Let's terminate the loop when Claude's response text contains 'Is there anything else I can help with?'" Why is this wrong, and what's the correct signal?

Model answer

Wrong because (1) Claude can return text alongside a tool call in the same response — your code would terminate while the agent is mid-task; and (2) phrasing varies non-deterministically, so you'd be writing regex against probabilistic surface output. The correct signal is stop_reason — structured metadata the API guarantees. "end_turn" means done; "tool_use" means continue.

1.2 Multi-agent orchestration 2 q
Q03 Task 1.2Context passing

A coordinator delegates a research task to a web search subagent and gets back 8 articles. Next, the coordinator wants the synthesis subagent to write a summary based on those articles. What MUST the coordinator do for synthesis to work?

Model answer

Include the article details and URLs directly in the synthesis subagent's Task prompt as structured metadata, not just raw content. Subagents have no shared memory; if it's not in the prompt, it doesn't exist for them. Pass content separated from metadata (URLs, titles, dates) so the synthesis agent can preserve attribution through the synthesis step.

Q04 Task 1.2Output gaps

Your multi-agent system produces final reports that are missing entire topic areas, even though every subagent's individual logs show clean execution. Where do you investigate first, and why?

Model answer

Investigate the coordinator's task decomposition first. Subagents are constrained by the assignments they receive — if those assignments are too narrow, no downstream agent can recover from that. Mental shortcut: gaps in output = decomposition problem = coordinator problem. Subagent-level fixes don't address the root cause.

1.3 Spawning & context passing 2 q
Q05 Task 1.3Missing context

Your coordinator successfully runs the web search subagent and gets back results. It then emits a Task call for the synthesis subagent — but the synthesis subagent's output references "no available sources" even though the search succeeded. What's the most likely cause, and how do you fix it?

Model answer

The coordinator passed the synthesis subagent a Task call without including the web search results in its prompt. Subagents have no shared memory; the synthesis agent has no idea the search even happened. Fix: include the search results — content plus metadata (URLs, titles, dates) — directly in the synthesis subagent's prompt.

Common wrong instinct: "increase the context window" — capacity isn't the issue, nothing was passed. "Have synthesis call web_search itself" — re-runs the search, defeats specialization.
Q06 Task 1.3Latency

Your research pipeline runs three independent subagents (web search, internal docs, statistics database) and total latency is 90 seconds. All three are independent — none depends on another's output. How do you cut this to ~30 seconds without changing the subagents themselves?

Model answer

Have the coordinator emit all three Task tool calls in a single response so they execute in parallel. The phrase that matters is single response: sequential calls across separate turns won't parallelize, even if you intend them to. Three 30-second subagents running concurrently = ~30 seconds total.

1.4 Workflow enforcement & handoff 2 q
Q07 Task 1.4Compliance threshold

Your customer support agent has a policy: no individual refund may exceed $500 without manager approval. Logs show that in 3% of cases, the agent processes refunds of $600–$800 anyway. What's the right fix, and why are prompt-based approaches insufficient here?

Model answer

Add a pre-tool-use (tool call interception) hook that blocks any process_refund call where amount exceeds $500 and redirects the agent to escalate_to_human. Prompts have a non-zero failure rate; when business rules require guaranteed compliance — anything financial, security, or compliance-related — only programmatic enforcement provides the deterministic guarantee. The 3% failure rate translates directly into financial exposure.

Q08 Task 1.4Human handoff

An AI agent escalates a billing dispute to a human. The human picks up the ticket and immediately asks the customer, "Can you tell me what's going on?" — frustrating the customer who already explained everything. What went wrong, and what specific information should the AI have included?

Model answer

The AI didn't compile a structured handoff for the human. The human reviewer has no access to the conversation transcript — they see only what the AI compiles. The handoff must include all six required fields: customer_id, conversation_summary, investigation_results, root_cause, recommended_action, reason_for_escalation. Without these, the human starts blind and the customer re-explains.

1.5 Agent SDK hooks 2 q
Q09 Task 1.5Heterogeneous data

Your agent integrates three MCP servers from different teams. Each returns customer status as a different type: integer 1, string "active", boolean true. The agent occasionally produces wrong conclusions when comparing customer states across these tools. What's the right fix?

Model answer

Implement a PostToolUse hook that normalizes the heterogeneous customer status formats — integer, string, boolean — into a single canonical representation before the agent processes them. Pick a format (probably string: "active"/"inactive") and have the hook convert all three sources to it. The agent then reasons over uniform data and never sees the inconsistency.

Q10 Task 1.5GDPR enforcement

You have a rule: the agent must never call delete_user_data if the conversation is from a region governed by GDPR without an additional consent verification step. A teammate proposes adding a strongly worded prompt instruction. Why is this insufficient, and what specific hook pattern do you use?

Model answer

Use a pre-tool-use (tool call interception) hook. Prompts are probabilistic and have a non-zero failure rate; GDPR compliance requires guaranteed enforcement because a non-zero failure rate exposes the company to regulatory risk. The hook intercepts every delete_user_data call, checks the conversation context for the region, verifies consent has been explicitly obtained when GDPR applies, and blocks the call otherwise.

1.6 Task decomposition 2 q
Q11 Task 1.6Attention dilution

For PRs touching 3–4 files the reviews are excellent. For PRs touching 12+ files, reviews become inconsistent — same code pattern flagged in one file, approved in another, obvious bugs missed. The team proposes upgrading to a model with a larger context window. Will this fix the problem?

Model answer

No. Attention dilution is independent of context window capacity. A bigger window is about how much can fit; attention is about how deeply the model focuses on each piece. Cramming more in often makes dilution worse. The fix is decomposition into focused passes — per-file local passes plus a separate cross-file integration pass.

Q12 Task 1.6Decomposition strategy

You're tasked with refactoring a legacy authentication module to use a modern token-based system. You don't know the module's structure or dependencies. Should you use a fixed pipeline (analyze → design → implement → test) or a dynamic adaptive approach? Why?

Model answer

Dynamic adaptive. The task is open-ended, the structure of the legacy module is unknown, and the right next step depends on what's discovered at each stage. A fixed pipeline assumes the design phase can be planned without knowing what's in the code. Dynamic adaptive lets the plan emerge: map structure → identify dependencies → prioritize → adapt as new dependencies surface during refactoring. Trigger words for dynamic adaptive: legacy, unfamiliar, unknown structure, open-ended.

1.7 Session state 2 q
Q13 Task 1.7Stale context

Yesterday you spent two hours investigating a payment processing bug. The agent read 25 files and identified three suspicious functions. Overnight, the team merged a major refactor that renamed several modules and restructured the payment flow. You want to continue today. Should you resume, fork, or start fresh? Why?

Model answer

Start fresh with an injected summary. The prior tool results — file contents, function signatures, dependency traces — are now stale because the codebase was refactored overnight. Resuming would carry those stale results forward, and the agent would reason over outdated data without any signal that it's wrong. The injected summary should contain conclusions from yesterday (suspected functions, hypotheses ruled out) — not raw tool results. The fresh session re-reads files as needed, getting current data.

Q14 Task 1.7Divergent exploration

You've spent 45 minutes analyzing a complex algorithm. Now you want to evaluate two different optimization strategies in parallel — one focused on memory efficiency, the other on CPU efficiency. The codebase hasn't changed. What mechanism do you use, and why?

Model answer

fork_session. You have a shared analysis baseline you don't want to redo, and you want to explore divergent approaches without one contaminating the other. Fork from the analysis baseline; one branch explores memory optimization, the other explores CPU optimization. Compare results. Running them sequentially in the same session would let the first strategy's reasoning bias the evaluation of the second.
