01.1
Task statement 1.1 · Agentic loops

The lifecycle, governed by a single signal.

On the exam: every question about loop control comes back to stop_reason. If you can recognize the three anti-patterns and explain why tool results must be appended, you'll get every Task 1.1 question right.

What an agentic loop actually is

An LLM by itself only produces text. To make it useful in production, we give it tools — but the model doesn't actually execute them. It says "I want to call this tool with these inputs." Your code runs the tool, returns the result, and the model decides what to do next. This back-and-forth is the agentic loop.

The control signal is structured

  • stop_reason = "tool_use" — the model wants something done. Run the tool, append the result, loop again.
  • stop_reason = "end_turn" — the model is finished. Exit the loop, return the response.
  • Tool results must be appended to the message history before the next API call. Without that, the model is reasoning blind on the next turn.

Hover over any node — or click the steps below — to walk the loop. The control signal is stop_reason, never text content.
!

Anti-patterns & exam traps

Click each to expand
  • 01
    Parsing natural language for completion signals.
    Searching the response text for phrases like "anything else?" is fragile. The model can return text alongside a tool call in the same response — your code would terminate while it's mid-task.
    Inspect stop_reason directly. "end_turn" means done; "tool_use" means continue.
    +
  • 02
    Iteration caps as the primary stopping mechanism.
    An iteration cap is a safety net against runaway loops, not control flow. If your loop terminates because it hit max_iterations, that's a bug — not a feature.
    Use the cap as a guardrail. Let stop_reason == "end_turn" drive normal termination.
    +
  • 03
    Treating text content as a completion indicator.
    "Claude returned some text, so we must be done" is a common but wrong inference. Text can accompany a tool call. Only stop_reason is the structured, guaranteed signal.
    Always inspect stop_reason explicitly before deciding to terminate.
    +
  • 04
    Pre-configured decision trees instead of model-driven decisions.
    Hand-coded routing (if user_says_X then call_Y) replaces the agent with a chatbot. The whole point of the loop is that Claude reasons about which tool to call.
    Provide good tool descriptions and let the model select. Reserve hard routing for compliance gates (Task 1.5).
    +
"Be explicit about what crosses boundaries. Whether the receiver is a subagent, a future session, or a human — they only know what you put in front of them."

01.2
Task statement 1.2 · Multi-agent orchestration

Hub and spoke. Always hub and spoke.

On the exam: when output has gaps, look at the coordinator's decomposition first. The most-tested concept is that subagents have no shared memory with the coordinator or each other.

The architecture

One coordinator at the centre. Specialized subagents around it. All communication routes through the coordinator — subagents never speak directly to each other. This isn't a design preference; it's how you preserve observability, consistent error handling, and controlled information flow.

Coordinator responsibilities, in order

  • Task decomposition. Break the request into subtasks. This is where most multi-agent failures originate.
  • Subagent selection. Decide which subagents to invoke based on the query. Not every request needs the full pipeline.
  • Context passing. Build each subagent's prompt with everything it needs — they inherit nothing.
  • Result aggregation. Merge findings, evaluate gaps, re-delegate if coverage is insufficient.
Figure 1.2 · Hub-and-spoke coordinator
Click "Animate flow" to walk through how a request fans out and aggregates back. Hover any node for its role.

The narrow decomposition trap

A research request: "impact of AI on creative industries." The coordinator decomposes it into AI in digital art, AI in graphic design, AI in photography. Every subagent executes correctly. The final report misses music, writing, and film entirely.

This is the canonical exam scenario. Distractor answers will blame the synthesis agent or the search agent. The bug is in the decomposition — and decomposition is the coordinator's job. When output has gaps, look at the coordinator's logs first.

!

Anti-patterns & exam traps

Click each to expand
  • 01
    Blaming downstream subagents for output gaps.
    If the coordinator's logs show narrow subtask assignments, the subagents executed correctly within their scope. Adding "coverage gap detection" to synthesis won't fix the missing topics.
    Investigate the coordinator's decomposition. Use goal-based prompts, not procedural ones, so it adapts.
    +
  • 02
    Direct subagent-to-subagent communication.
    It breaks observability, error handling, and information flow control. You lose the central audit point that makes multi-agent systems debuggable.
    Route every byte through the coordinator. No exceptions.
    +
  • 03
    Always running the full pipeline.
    A simple fact-check doesn't need synthesis and report generation. Forcing every query through every subagent wastes tokens and degrades results when subagents process irrelevant context.
    Let the coordinator dynamically select subagents based on query complexity.
    +
  • 04
    "Subagents inherit the coordinator's context."
    They don't. Ever. Each subagent runs as a separate Claude instance with an empty conversation. Whatever isn't in its prompt doesn't exist for it.
    Build every subagent's prompt with explicit content, metadata, and goal. Treat it as a stranger.
    +
01.3
Task statement 1.3 · Spawning & context passing

The mechanics of delegation.

On the exam: questions about parallel spawning, fork_session, and the Task tool's allowedTools requirement. Memorize that parallel spawning happens within a single response.

The Task tool

Subagents are spawned by the coordinator calling a tool named Task. From the coordinator's perspective, spawning a subagent looks identical to calling any other tool. The coordinator's allowedTools must include "Task" — without it, the coordinator literally cannot delegate.

Three slots in every subagent prompt

  • Content — the actual data: articles, search results, document excerpts.
  • Metadata — source URLs, document names, page numbers, publication dates. Kept separate from content to preserve attribution through synthesis.
  • Goal & quality criteria — what good output looks like. Goal-based prompts let subagents adapt; procedural prompts lock them into fixed sequences.
Figure 1.3 · Sequential vs parallel spawning
Click "Toggle mode" to compare sequential vs parallel spawning. The fix: emit multiple Task tool calls in a single coordinator response.

fork_session — divergent exploration

Different mechanism, different use case. fork_session creates an independent branch from a shared baseline. Both branches start with the full prior context, then diverge.

The classic case: you've spent 20 minutes analyzing a codebase. Now you want to evaluate two refactoring approaches without redoing the analysis. Fork from the analysis baseline; one branch tries Approach A, the other Approach B; compare results.

MechanismPurposeContext relationship
Task Delegate specialized work Subagent gets only what coordinator passes
fork_session Explore divergent approaches Both forks share the entire baseline, then diverge
--resume Continue prior work Same single thread, picked up later
!

Anti-patterns & exam traps

Click each to expand
  • 01
    Sequential Task calls across separate turns when latency matters.
    Tool calls emitted in different turns execute one after another. Three 30-second subagents = 90 seconds.
    Emit multiple Task tool calls in a single coordinator response. Your code runs them concurrently.
    +
  • 02
    Forgetting "Task" in allowedTools.
    If Task isn't in the coordinator's allow-list, it cannot spawn anything. The exam will describe a coordinator that "isn't delegating" — this is the answer.
    Add "Task" to the coordinator's allowedTools. Subagents typically should NOT have it (no recursive spawning).
    +
  • 03
    Using fork_session to delegate to specialists.
    Wrong tool. Fork is for divergent exploration from a shared baseline; Task is for delegation. They're not interchangeable.
    Task → delegation. fork_session → parallel exploration of alternatives.
    +
  • 04
    Procedural prompts dictating step-by-step subagent behavior.
    "Step 1: search X. Step 2: filter by Y. Step 3..." locks the subagent into a fixed sequence that can't recover from edge cases.
    Specify the goal and quality criteria. Let the subagent decide how to achieve them.
    +
01.4
Task statement 1.4 · Workflow enforcement & handoff

Probabilistic guidance · deterministic gates.

On the exam: when failure has financial, security, or compliance consequences, the answer is programmatic enforcement — not a better prompt. Memorize the human-handoff field list.

The decision rule

One sentence. Memorize it. Probabilistic compliance is fine for guidance. Deterministic compliance requires programmatic enforcement.

Said another way: prompts are suggestions the model usually follows. Hooks are gates the model cannot bypass.

Probabilistic · WRONG for compliance
Prompt instruction

"Always call get_customer before any order operations."

# 12% failure rate in production if user_request: # model usually follows the instruction # sometimes skips it # cost: misidentified accounts, wrong refunds
Deterministic · CORRECT for compliance
Pre-tool-use hook

Hook intercepts process_refund calls before they execute.

def pre_tool_use_hook(tool, args, history): if tool in sensitive_ops: if not verified_id_in(history): return BLOCK return ALLOW # 0% failure rate

Structured handoff to humans

The other half of this task: when the agent escalates, the human reviewer does not have access to the conversation transcript. They see only what the AI compiled into a structured handoff. Six fields, every time.

Anti-patterns & exam traps

Click each to expand
  • 01
    "Improve the prompt to enforce ordering."
    When the question describes financial, security, or compliance failures with a non-zero failure rate, prompt-improvement options are distractors. They reduce the rate but never to zero.
    Programmatic enforcement (pre-tool-use hook) is the answer. Prompts can stay for naturalness — but the hook is the safety net.
    +
  • 02
    "Add few-shot examples showing correct sequencing."
    Same trap as #1. Few-shot examples are probabilistic. They help, but never produce guaranteed compliance.
    For zero-failure requirements: hooks. Few-shot is for ambiguous-case handling, not compliance gates.
    +
  • 03
    "The human agent will see the conversation history."
    A baked-in distractor assumption. The human gets only the structured handoff payload — nothing else.
    Compile all six fields explicitly: customer_id, conversation_summary, investigation_results, root_cause, recommended_action, reason_for_escalation.
    +
  • 04
    Handling multi-concern requests one at a time across turns.
    A customer with three concerns shouldn't get a sequential investigation. State gets lost; resolution becomes inconsistent.
    Decompose into distinct items, investigate in parallel within a single turn, synthesize a unified resolution.
    +
01.5
Task statement 1.5 · Agent SDK hooks

Two hook patterns. Two distinct jobs.

On the exam: pre-tool-use blocks outgoing calls (compliance), PostToolUse transforms incoming results (normalization). Don't confuse the directions.

The two patterns

Pre-tool-use hook fires before a tool runs. Inspects the proposed tool call and decides: allow, block, or modify. Used for compliance gates — refund thresholds, identity prerequisites, GDPR consent.

PostToolUse hook fires after a tool runs but before the model sees the result. Transforms the tool's output before it enters conversation history. Used for data normalization across heterogeneous backends.

Figure 1.5 · Hook positions in the loop
Two hooks sit between Claude and the tools, doing opposite jobs. Pre-hook gates outgoing calls; PostToolUse cleans incoming results.

Decision framework

If the requirement is...Then use...
Guaranteed compliance with a business rulePre-tool-use hook
Consistent data format across heterogeneous toolsPostToolUse hook
Style, tone, communication preferencePrompt
Tool selection guidancePrompt + good tool descriptions
Failure rate must be zeroHook
Probabilistic improvement is acceptablePrompt
!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Use a PostToolUse hook to enforce business rules."
    Wrong direction. PostToolUse runs after the tool already executed — too late to block a refund.
    Pre-tool-use hooks block calls before they run. PostToolUse only transforms results.
    +
  • 02
    "Use a pre-tool-use hook to normalize data formats."
    Wrong direction. Pre-tool-use intercepts the call, not the result. By the time you have data to normalize, the tool has already returned.
    PostToolUse is where you transform results. Pre is for blocking; Post is for cleaning.
    +
  • 03
    "Add prompt instructions to handle different timestamp formats."
    Probabilistic fix to a deterministic problem. The model will get it right most of the time — and silently wrong sometimes.
    PostToolUse normalization. The model never sees the inconsistency.
    +
  • 04
    "Hooks should be used for everything to maximize control."
    Overcorrection. Hooks add latency and code complexity. Tool selection guidance, communication style, and optional behaviors belong in prompts.
    Hooks for guarantees, prompts for guidance. Use both.
    +
01.6
Task statement 1.6 · Task decomposition

Attention dilution & the multi-pass fix.

On the exam: when a single agent reviews many files at once and produces inconsistent results, the answer is decomposition into focused passes — never a bigger context window.

Two decomposition strategies

  • Fixed sequential pipelines (prompt chaining). Decide the sequence upfront. Each step's output feeds the next. Use when the structure is known and predictable.
  • Dynamic adaptive decomposition. Generate the plan as you go, based on findings. Use for open-ended tasks where the right next step depends on what's already discovered.

The attention dilution problem

A pull request modifies 14 files. A single review pass produces bizarre output — some files get detailed feedback, others superficial; obvious bugs are missed; the same code pattern is flagged in one file and approved in another.

This is not a context window issue. The 14 files might fit comfortably. The problem is that the model can't deeply focus on each one when juggling thirteen others. This is a cognitive load issue, and a bigger window doesn't fix it.

A bigger context window doesn't fix attention dilution. Decomposition into focused passes does. Click "Toggle approach" to compare.
!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Use a larger context window to handle more files."
    Attention dilution is independent of capacity. A million-token window doesn't increase the model's ability to deeply focus on each item.
    Split into per-file passes plus a separate integration pass for cross-file data flow.
    +
  • 02
    "Run multiple passes and require consensus."
    Suppresses real findings that only one pass catches. You'd reduce false positives at the cost of missing true positives.
    Per-file local passes + integration pass. Don't filter by consensus.
    +
  • 03
    "Use a fixed pipeline for an open-ended exploration."
    Forces a plan onto a task that needs to discover its plan as it goes. Misses high-impact areas.
    Dynamic adaptive: investigate first, generate the plan from findings, adapt as new dependencies surface.
    +
  • 04
    "Force developers to submit smaller PRs."
    Shifts burden to humans without fixing the system. The bug is still there; you're just hiding it by avoiding the trigger.
    Fix the review architecture, not the workflow around it.
    +
01.7
Task statement 1.7 · Session state

Resume, fork, or start fresh.

On the exam: when prior tool results are stale (files changed overnight), the answer is fresh session with injected summary — not resume. This is the trap most candidates miss.

Three mechanisms · three jobs

  • --resume <name> — continue a prior session. Same single thread, picked up later. Use when prior context is mostly still valid.
  • fork_session — branch from a shared baseline to explore divergent approaches. Both forks start with the full prior context.
  • Fresh session + injected summary — abandon the prior session entirely. Start new. Inject only the conclusions from before. Use when prior tool results are stale.

The stale context trap

You spent yesterday investigating a codebase. The agent read 40 files, called 60 tools. Overnight, the codebase changed significantly — files renamed, functions refactored. Today you try to resume.

The prior context contains tool results that no longer match reality. References to functions that don't exist anymore. The agent reasons over stale data and produces wrong conclusions — confidently, because it has no way to know its information is outdated.

Top of the diagram: the decision tree. Bottom: the trap to avoid. Click "Walk paths" to step through each option.
!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Resume the session after the codebase changed."
    The most-tested trap in this task statement. Resuming carries forward stale tool results; the agent reasons confidently over outdated data.
    Fresh session + injected summary. Carry forward conclusions, not raw tool results.
    +
  • 02
    "Use fork_session to continue work after a break."
    Wrong tool. Fork is for parallel divergent paths from a shared baseline, not picking up where you left off.
    --resume for continuation. fork_session for parallel exploration.
    +
  • 03
    "Always start fresh to avoid stale context."
    Overcorrection. When context is still valid, resuming preserves nuance and saves significant work that summaries lose.
    Match the mechanism to the situation: valid → resume; divergent → fork; stale → fresh + summary.
    +
  • 04
    "Tell the agent the codebase changed and let it figure out what's stale."
    Insufficient. The agent has no mechanism to identify which specific tool results are now wrong.
    Either name the changed files explicitly (resume + targeted re-analysis) or start fresh with summary.
    +
Hooks for guarantees. Prompts for guidance. Decomposition for focus. Explicit handoff for everything that crosses a boundary.
