Part A · Tool interface design (Task 2.1)

Three tools, one ambiguous pair.

You're building a customer-support agent. Design three MCP tools where two have similar enough descriptions to cause misrouting in production. Then rewrite both descriptions to fix the ambiguity.

Scenario

You're configuring MCP tools for a customer support agent that handles inquiries about customers and their orders. Three tools are needed:

  • One that retrieves a customer profile by customer ID.
  • One that retrieves an order by order ID.
  • One that processes a refund for a specific order.
Your task
Design the three tools — and bake in the ambiguity
  1. Write a thin, minimal description for each tool — exactly the kind a junior engineer would commit on a Friday afternoon.
  2. Make the customer-lookup tool and the order-lookup tool sound nearly identical, so production logs would show misrouting on queries like "check #12345" where the ID shape is ambiguous.
  3. Then rewrite all three descriptions to production grade — purpose, input format, example queries, edge cases, and an explicit boundary statement that says when to use each tool versus the others.

Format each tool as a JSON object with name, description, and input_schema fields. The before-and-after is what the exam will test.

Anti-pattern · the ambiguous pair

The descriptions below look reasonable in isolation, but side by side they're a coin flip. get_customer retrieves "customer information" and lookup_order retrieves "order details" — both accept ID-shaped strings, both return generic information. Production logs will show 10–15% misrouting on ambiguous queries.

tools/v0_thin.json[
  {
    "name": "get_customer",
    "description": "Retrieves customer information.",
    "input_schema": {
      "type": "object",
      "properties": {
        "id": { "type": "string" }
      },
      "required": ["id"]
    }
  },
  {
    "name": "lookup_order",
    "description": "Retrieves order details.",
    "input_schema": {
      "type": "object",
      "properties": {
        "id": { "type": "string" }
      },
      "required": ["id"]
    }
  },
  {
    "name": "process_refund",
    "description": "Refunds an order.",
    "input_schema": {
      "type": "object",
      "properties": {
        "order_id": { "type": "string" },
        "amount": { "type": "number" }
      },
      "required": ["order_id", "amount"]
    }

Why it fails
Symmetric descriptions

"Retrieves customer information" and "Retrieves order details" share the same verb and shape. When the user says "check #12345," neither description tells Claude which tool to pick.

Why it fails
No input format hints

Both schemas accept any string. Claude has nothing to use as a discriminator — no regex, no example shape, no boundary that says "use this when the input looks like CUST-, that one when it looks like ORD-."

Production grade · five-component descriptions

Each description below has the five components: purpose, input format, example queries, edge cases, and boundary. Names are tightened (get_customer_profile beats get_customer) and the input schemas now describe ID shapes so Claude has structural cues alongside the prose.

tools/v1_production.json[
  {
    "name": "get_customer_profile",
    "description": (
      "Retrieves a customer's profile (name, email, "
      "phone, addresses, lifetime value, account status) "
      "by customer ID. "
      "Input: CUST-XXXXX or 6-digit numeric "
      "(e.g., 'CUST-48201', '482015'). "
      "Use for queries about a person's account, "
      "contact details, or order HISTORY summary. "
      "NOT for individual order details — "
      "use lookup_order with the order ID instead. "
      "Returns null profile (not error) on miss."
    ),
    "input_schema": {
      "type": "object",
      "properties": {
        "customer_id": {
          "type": "string",
          "pattern": "^(CUST-)?\\d{6}$",
          "description": "6-digit ID, optional CUST- prefix"
        }
      },
      "required": ["customer_id"]
    }
  },
  {
    "name": "lookup_order",
    "description": (
      "Retrieves a single order by order ID. Returns "
      "items, quantities, ship status, tracking, and "
      "refund eligibility. "
      "Input: ORD-XXXXX or 5-digit numeric "
      "(e.g., 'ORD-12345', '12345'). "
      "Use for any query about a SPECIFIC order — "
      "shipment status, contents, delivery date. "
      "NOT for customer-level data (lifetime value, "
      "saved addresses) — use get_customer_profile. "
      "Returns null order (not error) on miss."
    ),
    "input_schema": {
      "type": "object",
      "properties": {
        "order_id": {
          "type": "string",
          "pattern": "^(ORD-)?\\d{5}$",
          "description": "5-digit ID, optional ORD- prefix"
        }
      },
      "required": ["order_id"]
    }
  },
  {
    "name": "process_refund",
    "description": (
      "Issues a refund against a specific order. "
      "Input: order_id (ORD-XXXXX) and amount in USD. "
      "Use only after lookup_order confirms the order "
      "exists and refund eligibility is verified. "
      "Refunds over $500 require manager approval — "
      "the tool returns a business error in that case. "
      "NOT a tool for store credit or partial returns "
      "of multi-item orders — those have separate tools."
    ),
    "input_schema": {
      "type": "object",
      "properties": {
        "order_id": {
          "type": "string",
          "pattern": "^ORD-\\d{5}$"
        },
        "amount": {
          "type": "number",
          "minimum": 0.01,
          "maximum": 500
        }
      },
      "required": ["order_id", "amount"]
    }
  }
]
Why it works
Differentiated purposes

Customer profile vs single-order details vs refund issuance. Each description names the SPECIFIC information returned, not generic "details."

Why it works
Explicit boundaries

"NOT for X — use Y instead" appears in every description. Claude reads these as routing hints. ID-shape patterns reinforce structurally.

Key point

The fix isn't more tools or fewer tools — it's better descriptions. Five components: purpose, input format, example queries, edge cases, and boundary. Boundary lines ("NOT for X — use Y instead") are the single highest-leverage addition.

Part B · Structured error responses (Task 2.2)

One tool, four failure modes.

Implement the process_refund tool's error handling so the agent can choose the right recovery action for every category — transient, validation, business, and permission. The error metadata is the contract.

The four categories — recap

Transient
Timeout, 503, network blip
isRetryable: true → retry with backoff
Validation
Bad input format or missing field
isRetryable: true → fix input, retry
Business
Policy violation
isRetryable: false → explain or escalate
Permission
Caller not authorized
isRetryable: false → surface auth issue
Your task
Implement process_refund with structured error responses
  1. Write the process_refund(order_id, amount) handler in Python.
  2. Return structured error responses for all four categories. Each must include isError, errorCategory, isRetryable, a customer-friendly message, and a details object with category-specific context.
  3. Make sure a "no order found" result is returned as success with an empty payload — not as an error. That distinction is the trap.

Concrete failures to handle: payment service timeout (transient), malformed order ID (validation), refund exceeds $500 cap (business), agent lacks refund role (permission), order ID not in database (success with empty result).

Helper functions

Centralize the response shape in two helpers — err() and ok() — so every code path produces consistent metadata. The agent reads errorCategory first, then isRetryable, then details.

refund_tool/responses.pydef err(category, retryable, message, details=None):
    return {
        "isError": True,
        "errorCategory": category,
        "isRetryable": retryable,
        "content": [{
            "type": "text",
            "text": message,
        }],
        "details": details or {},
    }

def ok(payload):
    return {
        "isError": False,
        "content": [{
            "type": "text",
            "text": json.dumps(payload),
        }],
    }

The handler — with all four categories plus the empty-result trap

Each branch tags the failure with the right category, sets isRetryable correctly for that category, and includes details the agent can show the user or use to plan the next step. The "no order found" branch returns ok — a successful query with an empty result is not an error.

refund_tool/handler.pyimport re
import json
from .responses import err, ok
from .auth import caller_has_role
from .db import order_db
from .payments import PaymentTimeout, payments_api

REFUND_CAP_USD = 500
ID_PATTERN = re.compile(r"^ORD-\d{5}$")

def process_refund(order_id, amount, *, caller):
    # 1. PERMISSION — caller can't refund at all
    if not caller_has_role(caller, "refund_agent"):
        return err(
            category="permission",
            retryable=False,
            message="You don't have permission to issue refunds.",
            details={
                "required_role": "refund_agent",
                "caller": caller.id,
                "escalation_path": "contact your manager",
            },
        )

    # 2. VALIDATION — input format is wrong
    if not ID_PATTERN.match(order_id):
        return err(
            category="validation",
            retryable=True,
            message="Order ID must look like ORD-12345.",
            details={
                "received": order_id,
                "expected_pattern": "ORD-\\d{5}",
                "hint": "Strip whitespace, prefix ORD- if missing.",
            },
        )

    if amount <= 0:
        return err(
            category="validation",
            retryable=True,
            message="Refund amount must be greater than zero.",
            details={"received": amount},
        )

    # 3. BUSINESS — request violates policy
    if amount > REFUND_CAP_USD:
        return err(
            category="business",
            retryable=False,
            message=(
                f"Refunds over ${REFUND_CAP_USD} require "
                "manager approval. I can't process this myself."
            ),
            details={
                "requested_amount": amount,
                "policy_limit": REFUND_CAP_USD,
                "escalation_path": "escalate_to_manager_queue",
                "customer_message": (
                    "This refund exceeds my limit — I'm "
                    "escalating to a manager who'll respond "
                    "within one business day."
                ),
            },
        )

    # Lookup order — and HANDLE EMPTY VS ACCESS FAILURE
    try:
        order = order_db.fetch(order_id, timeout=5)
    except TimeoutError:
        # 4. TRANSIENT — service is unavailable
        return err(
            category="transient",
            retryable=True,
            message="Order lookup timed out. Please retry.",
            details={
                "service": "order_db",
                "timeout_seconds": 5,
                "suggested_backoff_ms": 250,
            },
        )

    if order is None:
        # EMPTY RESULT — query succeeded, answer is "no match"
        # NOT an error: agent should tell user "no order found"
        return ok({
            "refunded": False,
            "order_found": False,
            "message": f"No order matching {order_id}.",
        })

    # Issue the refund — payment service may also fail
    try:
        receipt = payments_api.refund(
            order=order, amount=amount, timeout=8
        )
    except PaymentTimeout:
        return err(
            category="transient",
            retryable=True,
            message="Payment service timed out. Please retry.",
            details={
                "service": "payments_api",
                "order_id": order_id,
                "amount": amount,
                "suggested_backoff_ms": 500,
            },
        )

    return ok({
        "refunded": True,
        "order_id": order_id,
        "amount": amount,
        "receipt_id": receipt.id,
    })

Key point

The "no order found" branch returns isError: false — successful query, empty result. If you flag this as an error, the agent retries a deterministic miss, escalates a normal answer, or hides the truth from the customer. Reserve isError: true for actual failures.

Part C · MCP server integration (Task 2.4)

Configure with environment expansion.

Configure the three tools as an MCP server in .mcp.json at the project root. Use environment variable expansion for credentials so secrets stay out of git, and pair it with a community server so a teammate gets both on clone.

Scenario

The three tools you designed in Part A live in an internal MCP server called customer-ops that authenticates against your billing platform. You also want every teammate to have the official GitHub MCP server so they can review related issues without setting it up themselves.

Your task
Write the configuration file and document the setup
  1. Choose the right scope: .mcp.json at the project root (committed) or ~/.claude.json (personal). Justify the choice.
  2. Configure both servers: the internal customer-ops server and the official GitHub server. Each needs its own credentials.
  3. Use environment variable expansion (${VAR}) for every secret. Nothing sensitive in the committed file.
  4. Add a short setup note that tells a new teammate which environment variables to set before running Claude Code.

The credentials are: a BILLING_API_KEY for the internal server, and a GITHUB_TOKEN for GitHub.

Why project scope, not user scope

Both servers are shared with the team. They belong to the project, not to your home directory. Project-level .mcp.json is version-controlled and ships with every clone — exactly the property we want. User-level ~/.claude.json would mean every teammate has to discover and replicate the setup themselves.

The credentials problem is solved separately, by environment variable expansion. The committed file references ${BILLING_API_KEY} and ${GITHUB_TOKEN}; each developer sets the variables in their own shell. The configuration ships; the secrets don't.

.mcp.json (project root, committed)

.mcp.json{
  "mcpServers": {
    "customer-ops": {
      "command": "node",
      "args": ["./mcp-servers/customer-ops/dist/index.js"],
      "env": {
        "BILLING_API_KEY": "${BILLING_API_KEY}",
        "BILLING_API_BASE": "https://billing.internal/api/v2",
        "REFUND_CAP_USD": "500"
      }
    },
    "github": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-github"
      ],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}
customer-ops
Internal server, custom build

Lives in the repo at mcp-servers/customer-ops/. Custom is the right call here — billing platform integration is team-specific and no community server matches your data model.

github
Community server, npx

Use the official MCP server for standard SaaS. Don't build a custom GitHub integration when one already exists, is maintained, and is widely tested.

README excerpt — onboarding note for new teammates

The setup note belongs near the top of the README so a new clone doesn't hit cryptic errors on first run.

README.md (excerpt)## MCP setup (one-time, per developer)

This repo configures two MCP servers in `.mcp.json`:

- **customer-ops** — internal billing tools (lookup, refund)
- **github** — official GitHub MCP server

Both read credentials from environment variables. Before
running Claude Code:

```bash
# customer-ops — request from #platform-access
export BILLING_API_KEY="..."

# github — create at github.com/settings/tokens
# scopes needed: repo, read:org
export GITHUB_TOKEN="ghp_..."
```

Add the exports to your shell profile (`~/.zshrc`,
`~/.bashrc`) so they persist across terminals.

If `claude` reports a server failed to start, check
that both variables are set:

```bash
env | grep -E "BILLING_API_KEY|GITHUB_TOKEN"
```

What NOT to do

Two anti-patterns the exam tests directly. Both look "convenient" and both leak secrets.

Anti-pattern
Hardcoded token in .mcp.json

Committing "GITHUB_PERSONAL_ACCESS_TOKEN": "ghp_AbCd..." ships your token to every contributor with repo access. Rotation requires updating every checkout. A leaked repo means a leaked token.

Anti-pattern
Configuring in ~/.claude.json

User scope is invisible to teammates. The setup works for you, fails silently for everyone else. The exam tests this exact failure mode — "new teammate can't see the servers."

Key point

Project scope (.mcp.json) shares; user scope (~/.claude.json) isolates. Environment variable expansion is what lets you commit shared configuration without committing shared secrets.
