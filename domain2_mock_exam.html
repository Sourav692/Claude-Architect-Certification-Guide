Question01
Customer SupportTool descriptions

Your customer support agent has two tools: get_customer ("Retrieves customer information") and lookup_order ("Retrieves order details"). Both accept ID-shaped strings. Production logs show 12% of "check my order #12345" queries route to get_customer. What's the most effective first step?

  • A Add 5-8 few-shot examples to the system prompt showing correct tool selection
  • B Expand each tool's description to include input formats, example queries, edge cases, and boundaries explaining when to use it versus the other
  • C Implement a routing layer that pre-parses each user message and selects the tool based on detected keywords
  • D Consolidate both tools into a single lookup_entity tool that routes internally
Correct: B

Tool descriptions are the primary selection mechanism. The root cause is inadequate descriptions; expanding them is the lowest-effort, highest-leverage fix.

A: Few-shot examples mask the underlying issue and grow tokens. C: A routing classifier replaces LLM reasoning with hand-coded heuristics — over-engineered. D: Consolidation is a valid architectural choice but it's a redesign, not a "first step."
Question02
Document ProcessingTool splitting

You have a generic analyze_document tool that handles fact-checking, summarization, and structured field extraction. Agents misuse it about 25% of the time — using it for summarization when extraction was needed, and vice versa. What's the right architectural fix?

  • A Add a task_type parameter to the tool so callers can specify what they want
  • B Rewrite the description with longer prose explaining each use case
  • C Split it into extract_data_points, summarize_content, and verify_claim_against_source — three tools with defined input/output contracts
  • D Force the tool with tool_choice selection on every call to ensure consistent behavior
Correct: C

Generic tools with mixed responsibilities cause selection ambiguity. Splitting into purpose-specific tools with defined contracts makes selection obvious — three tools, three jobs, three clean signals.

A: Mode flags push the ambiguity into the input parameter; selection is still unclear. B: Long descriptions for a single tool can't compete with three distinct tool boundaries. D: Forcing the same tool doesn't fix when it should be used.
Question03
Refund ProcessingError categories

Your process_refund MCP tool gets a request for $750 when company policy caps refunds at $500. What error response should it return?

  • A isError: true, errorCategory: "transient", isRetryable: true
  • B isError: true, errorCategory: "validation", isRetryable: true, with a corrected amount
  • C isError: true, errorCategory: "business", isRetryable: false, with a customer-friendly message and the policy limit in details
  • D isError: false with the refund silently capped at $500
Correct: C

Policy violations are business errors, not transient or validation. They are NOT retryable — retrying with the same amount fails again. Customer-friendly messaging and structured details enable the agent to explain or escalate appropriately.

A: Wastes retries on a deterministic policy block. B: Validation implies bad input format; the format is fine, the value violates policy. D: Silent capping breaks user expectations and audit trails.
Question04
Multi-Agent ResearchError propagation

A web search subagent times out while researching a complex topic. You're designing how the failure information flows back to the coordinator. Which approach best enables intelligent recovery?

  • A Return structured error context including failure type, the attempted query, partial results, and potential alternative approaches
  • B Return a generic "search unavailable" status only after the subagent's internal exponential-backoff retry logic exhausts
  • C Catch the timeout inside the subagent and return an empty result set marked as successful so the coordinator can proceed
  • D Propagate the timeout exception directly to a top-level handler that terminates the entire research workflow
Correct: A

Structured error context gives the coordinator everything it needs to choose recovery: retry with a different query, route to a different subagent, or proceed with partial results and annotate gaps.

B: Generic status strips the signal needed for intelligent recovery. C: Silent suppression — coordinator synthesizes from incomplete data, doesn't know it failed. D: Over-aggressive — kills a workflow that could have recovered.
Question05
Multi-Agent ResearchScoped tools

Your synthesis agent frequently needs to verify simple facts (dates, names, statistics) while combining findings. Currently it returns control to the coordinator, which invokes the web search agent, then re-invokes synthesis with results — adding 40% latency. Telemetry shows 85% of these verifications are simple fact-checks; 15% need deeper investigation. What's the most effective approach?

  • A Give the synthesis agent a scoped verify_fact tool for simple lookups; complex verifications continue routing through the coordinator
  • B Have the synthesis agent batch all verification needs and return them at the end of its pass for the coordinator to handle
  • C Give the synthesis agent access to the full set of web search tools so it can handle any verification directly
  • D Have the web search agent proactively cache extra context around each source during initial research to anticipate what synthesis might need
Correct: A

Least-privilege applied to tool distribution. The 85% common case gets a scoped tool inline; the 15% complex case still routes through the coordinator. Eliminates round trips for high-frequency simple lookups without over-provisioning.

B: Batching breaks synthesis flow — synthesis often needs verified facts mid-pass. C: Over-provisioning. Synthesis agent will start doing research instead of synthesizing. D: Speculative caching — unreliable prediction of what will be needed.
Question06
MCP SetupConfiguration scope

A new team member clones your repo and runs Claude Code. They report none of the MCP servers you set up are available to them. You configured GitHub, Jira, and your internal billing server in ~/.claude.json on your machine. What's the fix?

  • A Move the server configurations from ~/.claude.json into a project-level .mcp.json committed to the repo, using environment variable expansion for credentials
  • B Have the new team member copy your ~/.claude.json to their home directory
  • C Add the server commands to a startup script in .claude/commands/ so they run when Claude Code starts
  • D Document the server URLs in the project README so new members can manually add them to their own ~/.claude.json
Correct: A

Project-level .mcp.json ships with the repo so every clone gets the servers automatically. Environment variable expansion keeps secrets out of git — each developer sets their own tokens locally.

B: Copying user-level config also copies your credentials — security violation. C: .claude/commands/ is for slash commands, not MCP server configuration. D: Manual setup is fragile and error-prone; the whole point of project scope is automation.
Question07
Codebase ExplorationTool selection

You need to find every file in a TypeScript codebase that imports the lodash library. Which built-in tool is appropriate?

  • A Glob with pattern **/*lodash* to match files by name
  • B Grep searching for the string from 'lodash' or require('lodash') across file contents
  • C Read every .ts file and inspect the import statements
  • D Bash with find . -name "*.ts" to list TypeScript files first, then inspect each
Correct: B

Grep searches file contents — exactly what you need to find import statements. Mental rule: contents = Grep, paths = Glob.

A: Glob matches paths only — would only catch files NAMED with "lodash" in the path. C: Reading every file blows context unnecessarily — the incremental anti-pattern. D: Bash + find is just listing files, doesn't actually search contents — same problem as A plus more steps.
