02.1
Task statement 2.1 · Tool interface design

Descriptions are the selection mechanism.

On the exam: every misrouting question reduces to inadequate tool descriptions. If you can name the five components of a good description and recognize when "splitting" or "renaming" beats "more prompt", you'll get every Task 2.1 question right.

What Claude actually reads when picking a tool

An LLM doesn't have intuition about your tools. It reads each tool's description field and matches it against the user's request. If two descriptions look similar, the model picks one — sometimes the right one, sometimes the other. The description IS the selection mechanism. Vague descriptions produce vague selection.

The five components of a production-grade description

  • Purpose — exactly what the tool does. Not "manages orders" — "retrieves order details by order ID."
  • Input format — accepted identifier shapes, expected types, validation patterns.
  • Example queries — one or two realistic invocations the tool handles.
  • Edge cases — what the tool does NOT handle, including empty results.
  • Boundary — when to use this tool versus a similar alternative in the same toolset.

Hover any node — or click "Walk steps" — to trace the selection. The lever is description quality, not classifiers or few-shot examples.

The misrouting problem in production

You have get_customer ("Retrieves customer information") and lookup_order ("Retrieves order details"). Both accept ID-shaped strings. Logs show 12% of "check order #12345" queries route to get_customer. The fix isn't a prompt patch — it's the descriptions. Compare:

Anti-pattern
Minimal description

Two functionally adjacent tools with near-identical phrasing. Claude has no signal to differentiate them.

{
  "name": "lookup_order",
  "description": "Retrieves order details"
}
Production grade
Five-component description

Purpose, input format, example, edge case, boundary. Claude can now disambiguate from get_customer.

{
  "name": "lookup_order",
  "description": (
    "Retrieves order details by order ID. "
    "Input: ORD-XXXXX or 5-digit numeric "
    "(e.g., '12345', 'ORD-12345'). "
    "Returns status, items, ship date. "
    "Use for any query mentioning order number "
    "or shipment status. NOT for customer "
    "profile data — use get_customer instead. "
    "Returns empty result (not error) on miss."
  )
}

Splitting, renaming, and the system prompt trap

When one tool does too many things, Claude misuses it. Generic analyze_document should split into extract_data_points, summarize_content, and verify_claim_against_source — three tools, three contracts, obvious selection.

Renaming is sometimes the cheaper fix. analyze_content in a web research toolset should become extract_web_results with a web-specific description — same function, dramatically clearer signal.

The subtle trap: a system prompt with keyword bleed will override great descriptions. If your prompt says "always begin by analyzing content" and you have an analyze_content tool, the model gravitates there regardless of fit. Audit prompts for keywords that match tool names.

Anti-patterns & exam traps

Click each to expand
  • 01
    Adding few-shot examples to fix a description problem.
    Examples in the system prompt mask the underlying issue but don't fix it. Tokens grow with every example. The model still has to reason from minimal descriptions on novel inputs.
    Expand the descriptions with input format, examples, and explicit boundary statements. Lowest effort, highest leverage.
    +
  • 02
    Building a routing classifier in front of the LLM.
    A keyword-based pre-router replaces the LLM's reasoning with hand-coded heuristics — exactly the thing tool selection is designed to avoid. Adds latency, breaks on edge cases, doesn't generalize.
    Trust the model. Give it good descriptions and let it pick. Reserve hard routing for compliance gates, not tool selection.
    +
  • 03
    Keeping a generic do-everything tool with mode flags.
    A tool that takes a task_type parameter and branches internally is opaque to the model. The description has to enumerate every mode; selection becomes the same ambiguity problem one level deeper.
    Split into purpose-specific tools with defined input/output contracts. Three small tools beat one generic tool.
    +
  • 04
    Ignoring system prompt keyword bleed.
    The exam tests this subtlety: even with great descriptions, a prompt phrase like "always start by analyzing the content" pulls Claude toward any analyze_* tool. Misrouting persists despite the fix to descriptions.
    Audit the system prompt for verbs and nouns that match tool names. Replace keyword-loaded phrasing with goal-based instructions.
    +
02.2
Task statement 2.2 · Structured error responses

isError is a flag, not a recovery strategy.

On the exam: questions about retry behavior, multi-agent error propagation, and the access-failure-vs-empty-result distinction. Memorize the four categories — transient, validation, business, permission — and the recovery action each implies.

The protocol minimum vs production reality

MCP defines a single isError: true flag on tool responses. That's the minimum. It tells the agent something failed, but not what kind of failure, not whether retry is appropriate, not what to tell the user. Production tools return structured error metadata alongside isError, and the agent reads that metadata to choose recovery strategy.

The four categories — and the action each implies

  • Transient — timeout, 503, network blip. isRetryable: true. Retry with backoff.
  • Validation — invalid input format or missing required field. Retry only after fixing input.
  • Business — policy violation (refund over limit, ineligible customer). Don't retry; explain to user or escalate.
  • Permission — caller not authorized for the resource. Don't retry; surface auth issue.
Figure 2.2 · Error category → recovery action
Hover any category to see its recovery action. The exam trap is uniform error responses; the fix is structured metadata so the agent can choose the right recovery.

Access failure vs valid empty result

This distinction trips up most candidates. They look similar but require different agent behavior:

CaseWhat happenedCorrect response
Access failure Database timeout, service unreachable, connection refused isError: true, errorCategory: "transient" — agent retries
Valid empty result Query succeeded; the answer is "no rows match" isError: false, empty array — agent accepts and continues

If your tool flags both with isError: true, the agent treats a successful "no orders found" the same as a database outage. Reserve the error flag for actual failures.

Anti-pattern
Generic uniform error

Same shape regardless of cause. Agent has no information to choose recovery.

def lookup_order(order_id):
    try:
        order = db.fetch(order_id)
        if not order:
            return {"isError": True,
                    "content": "failed"}
        return {"isError": False,
                "content": order}
    except Exception:
        return {"isError": True,
                "content": "failed"}
Production grade
Structured per-category metadata

Each failure mode tagged. Empty result is success. Agent knows what to do.

def lookup_order(order_id):
    if not re.match(r"^(ORD-)?\d{5}$", order_id):
        return err("validation", retry=True,
                   msg="Bad ID format")
    try:
        order = db.fetch(order_id, timeout=5)
    except TimeoutError:
        return err("transient", retry=True,
                   msg="Service timeout")
    if not order:
        # empty != failure
        return ok({"order": None, "found": False})
    return ok(order)

Multi-agent error propagation

In a coordinator-subagent system, errors propagate in layers. Each layer has a different responsibility:

  • Subagent first — handle local recovery on transient failures (one or two retries within the subagent before escalating up).
  • Subagent propagates — only what it cannot resolve, including failure type, what was attempted, partial results gathered, and possible alternative approaches.
  • Coordinator decides — retry with a modified query, route to a different subagent, or proceed with partial results and annotate gaps in the final output.
!

Anti-patterns & exam traps

Click each to expand
  • 01
    Returning generic "Operation failed" for every error.
    Strips signal the agent needs to make recovery decisions. The agent retries permission errors (waste), gives up on transient ones (lost requests), and surfaces transient failures to users (bad UX).
    Tag each error with errorCategory and isRetryable. Match recovery strategy to category.
    +
  • 02
    Marking "no matches found" as an error.
    Empty results from a successful query are normal data, not failure. Conflating them with access failures wastes retries and breaks downstream reasoning that handles "the answer is zero" perfectly fine.
    Empty result = isError: false, empty array. Reserve the error flag for actual failures.
    +
  • 03
    Subagent silently swallows error and returns empty success.
    The coordinator has no idea something failed. It synthesizes a final answer from incomplete data and presents it confidently. Worse than a visible failure.
    Subagent attempts local recovery, then propagates with structured context — failure type, what was attempted, partial results, alternative approaches.
    +
  • 04
    Terminating the entire workflow on the first subagent failure.
    Over-aggressive escalation. A single transient timeout in the web search subagent shouldn't kill a research pipeline that has internal docs and statistics still running.
    Coordinator catches the propagated error, decides whether to retry or proceed with partial results, and annotates coverage gaps in the final output.
    +
02.3
Task statement 2.3 · Tool distribution & tool_choice

Selection reliability degrades with tool count.

On the exam: the 18-tool degradation, the optimal 4-5 per agent rule, the 85% pattern for scoped cross-role tools, and when to use auto vs any vs forced selection. Distribution is structural; tool_choice is the API-level control.

Why too many tools degrades selection

An agent given 18 tools misroutes far more often than the same agent given 4-5 focused tools. Two failure modes drive this:

  • Decision complexity — Claude evaluates every tool description against the query. More tools means more candidate matches and more chances for a near-miss to win selection.
  • Cross-specialization misuse — agents with tools outside their role tend to invoke them inappropriately. A synthesis agent with web search access starts doing its own research instead of synthesizing what the search agent gathered.

The remedy is structural: distribute tools across agents so each gets only what its role requires.

Figure 2.3 · Scoped tool distribution
Hover any agent to see its scoped tool set. Each subagent gets 3-4 role-specific tools. Synthesis gets one scoped cross-role tool for high-frequency exceptions.

The 85% pattern — scoped cross-role tools

Production scenario: your synthesis agent frequently needs to verify simple facts (dates, names, statistics) while combining findings. Currently it routes through the coordinator → web search agent → back to synthesis. That adds 2-3 round trips and 40% latency.

Telemetry shows 85% of these verifications are simple fact-checks and 15% need deeper investigation. The right answer is NOT "give synthesis all the web tools" (over-provisioning). The right answer is a scoped verify_fact tool that handles the 85% inline. The 15% complex cases still route through the coordinator.

This is least-privilege applied to tool distribution. Give the agent exactly what it needs for the common case; route exceptions through the coordinator.

Replacing generic tools with constrained ones

When a tool gets misused, often the fix is replacing the generic version with a constrained one:

  • fetch_url (anyone can fetch anything) → load_document (validates the URL is in your document corpus).
  • analyze_content (vague) → extract_web_results (web-specific contract).
  • query_database (open-ended) → lookup_customer_by_id (one query shape).

The constrained version both prevents misuse and gives Claude a clearer selection signal.

tool_choice — API-level control

Three modes, three use cases:

ModeBehaviorWhen to use
"auto" Claude decides whether to call a tool or return text Standard conversational agent loop
"any" Claude must call SOME tool (its pick) Guarantee structured output from multiple valid extraction schemas
{"type": "tool", "name": "..."} Claude must call THIS tool A specific step must happen first (e.g., extract metadata before enrichment)
Anti-pattern
tool_choice: "auto" when output must be structured

Document type is unknown; you have three extractors. With "auto", Claude often returns conversational text instead of calling one. Output isn't parseable.

client.messages.create(
  tools=[invoice_tool,
         receipt_tool,
         contract_tool],
  tool_choice={"type": "auto"},
  messages=[...])
# may return text, not a tool call
Production grade
tool_choice: "any" guarantees a tool call

Claude picks which extractor based on the document, but MUST call one. Output is always structured.

client.messages.create(
  tools=[invoice_tool,
         receipt_tool,
         contract_tool],
  tool_choice={"type": "any"},
  messages=[...])
# guaranteed tool call
!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Give every agent every tool for flexibility."
    More tools means more selection error. The synthesis agent with web search access starts doing research instead of synthesizing. The model isn't disciplined about staying in role unless its toolset enforces the boundary.
    Restrict each subagent to 3-5 role-specific tools. Add scoped cross-role tools only for documented high-frequency needs.
    +
  • 02
    "Batch verifications and return them at the end."
    Synthesis often needs verified facts mid-pass to phrase a sentence correctly. Batching forces a blocking dependency that breaks the synthesis flow and produces hedged language ("based on available sources...") instead of crisp claims.
    Scoped verify_fact handles common cases inline. Complex verifications still route through the coordinator.
    +
  • 03
    tool_choice: "auto" when conversational text leaks instead of structured output.
    "auto" lets Claude return text. If the downstream consumer needs JSON from a tool call, "auto" is wrong — Claude often takes the easy path and replies in prose.
    Use tool_choice: "any" when you need a guaranteed tool call. Forced selection when a SPECIFIC tool must run.
    +
  • 04
    Coordinator with execution tools instead of just Task.
    A coordinator that has both Task AND web search will sometimes do the work itself instead of delegating. The whole point of the coordinator-subagent pattern is delegation; giving the coordinator execution tools blurs that boundary.
    Coordinator gets Task only. Subagents get the role-specific execution tools.
    +
02.4
Task statement 2.4 · MCP server integration

Project scope shares; user scope isolates.

On the exam: project-level vs user-level configuration, environment variable expansion for secrets, MCP resources for content catalogs, and the build-vs-use decision. The wrong scope choice either hides servers from teammates or commits credentials to git.

MCP primitives, briefly

An MCP server is a process that advertises two things to Claude: tools (actions Claude can invoke — verbs like create_issue) and resources (content catalogs Claude can read — nouns like an issue summary or schema doc). Resources matter because they reduce exploratory tool calls; the agent sees the inventory upfront instead of probing for it.

Two configuration scopes

  • Project-level — .mcp.json in the repo root. Version-controlled. Shared with every teammate who clones the repo.
  • User-level — ~/.claude.json in the home directory. Personal. Not shared.
  • Both load simultaneously at startup. All tools become available to the agent.
Figure 2.4 · Project vs user scope
Hover either scope to see when to use it. The exam tests one specific failure mode: team servers configured in user scope and therefore invisible to teammates.

Environment variable expansion — never commit secrets

You don't hardcode tokens in .mcp.json. You reference environment variables that get expanded at startup. Each developer sets the variable in their own shell. The committed file stays clean.

Anti-pattern
Hardcoded token in committed file

Every contributor's GitHub token is now in version control. Rotation is painful. Anyone with read access has access to your account.

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y",
        "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "ghp_AbCd..."
      }
    }
  }
}
Production grade
Environment variable expansion

Each developer sets GITHUB_TOKEN in their shell. The file commits cleanly. Rotation is trivial.

{
  "mcpServers": {
    "github": {
      "command": "npx",
      "args": ["-y",
        "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_TOKEN": "${GITHUB_TOKEN}"
      }
    }
  }
}

MCP resources — content catalogs the agent can see

Resources are often-forgotten on the exam. They're how an MCP server exposes a content inventory to the agent without forcing exploratory tool calls. Pattern: tools for actions, resources for content catalogs.

If your agent has to call list_issues, then get_issue for each, that's a wasted round trip per item. Expose the issue catalog as an MCP resource and the agent sees the full inventory immediately.

Build vs use — order of preference

  • Existing community MCP server first (Jira, GitHub, Slack, Postgres). Battle-tested, free, maintained.
  • Custom MCP server only when team-specific workflows aren't covered. Internal billing systems, proprietary databases, custom workflow engines.
  • Don't build a custom Jira server when one exists. The exam tests whether you'll over-engineer.

Description quality — built-in tools as competitors

When you connect an MCP server, its tools coexist with built-ins (Read, Grep, Bash). If your custom MCP description is thin, Claude prefers the built-in tool even when the MCP one is more capable. A custom query_codebase_index with description "Searches code" loses to Grep every time. Rewrite the description to state explicitly what the MCP tool does that the built-in can't — semantic similarity, ranked results, cross-file concept search.

!

  • 01
    Configuring team-shared servers in user scope.
    User-level config lives in your home directory and never reaches teammates. They clone the repo, run Claude Code, and none of "your" servers are available — because they were yours, not the project's.
    Move team-shared server configs to .mcp.json in the repo root with env var expansion for credentials.
    +
  • 02
    Hardcoded credentials in .mcp.json.
    Every commit ships your tokens to whoever has repo access. Rotation requires updating every developer's checkout. A leaked repo means leaked credentials.
    Use ${ENV_VAR} expansion in the env block. Each developer sets the variable locally.
    +
  • 03
    Building a custom MCP server when a community one exists.
    You're committing to maintenance, security, and capability parity with what an existing server already does. Time better spent on team-specific integrations the community can't provide.
    Use the official server for standard SaaS (Jira, GitHub, Slack). Build custom only for proprietary internal systems.

  • 04
    Thin MCP tool descriptions — Claude prefers the built-in.
    Built-in tools have rich, model-trained descriptions. A custom MCP tool with "Searches code" loses every selection contest to Grep, even when it would do the job better.
    Write descriptions that explicitly state what the MCP tool does that the built-in can't. Cite capability differences directly.

02.5
Task statement 2.5 · Built-in tools

Match the tool to the task.

On the exam: Grep vs Glob (the most-tested distinction), Edit's non-unique-match failure mode and Read+Write fallback, and incremental codebase exploration. The traps cluster around using the wrong tool for the search intent.

The cheatsheet

  • Grep — search file contents for patterns (function names, error strings, import statements).
  • Glob — find files by name or path pattern (**/*.test.tsx, src/**/*.py).
  • Read — load full file contents.
  • Write — create or overwrite a file.
  • Edit — targeted modification using unique text matching.
  • Bash — execute shell commands.

Grep vs Glob is the single most-tested distinction. "Find all callers of validateUser" is Grep — searching contents for the function name. "Find all .test.tsx files" is Glob — matching paths by pattern.

Figure 2.5 · Built-in tool selection
Hover any branch to see the decision rule. The most-tested split is Grep (contents) vs Glob (paths).

The Edit failure mode

Edit replaces a unique text snippet with a new one. If the snippet appears more than once in the file, Edit fails with a non-unique-match error. The fallback is Read the full file → Write the modified version.

Don't try to make Edit work by adding more context lines indefinitely. At some point the file is just too repetitive, and Read+Write is the right move.

Anti-pattern
Glob for content search

Glob only matches paths. Searching for files containing "lodash" by extension misses the actual goal — finding files that import the library.

# wrong tool
glob("**/*lodash*")
# matches files NAMED lodash-something,
# misses every file that imports lodash
Production grade
Grep for content search

Grep searches inside files for the actual import statement. Returns every file that uses lodash, regardless of file name.

# right tool
grep("from 'lodash'|require\\('lodash'\\)",
     glob="**/*.ts")
# every file that imports lodash

Incremental exploration — the right way to read a codebase

The exam tests one specific anti-pattern: dumping every file into context to "understand" a codebase. Wrong. The correct approach is incremental:

  • Start with Grep to find entry points or key references — main, app.listen, error messages from a stack trace.
  • Read those specific files to understand the immediate scope.
  • Follow imports with more Read calls to trace flow.
  • Repeat until you've answered the question.

Concrete: tracing all callers of a function exported through wrapper modules. Use Grep to find every export of the name. For each export, Grep again to find imports that reference it. For each importer, Read just enough to understand the call site. Build understanding by following references — never by reading everything.

!

Anti-patterns & exam traps

Click each to expand
  • 01
    Glob for content search.
    Glob matches paths, not contents. Searching for files that import lodash with a glob pattern returns files NAMED with "lodash" — not files USING lodash.
    Grep for the import statement (the content). Glob only when the goal is a path-pattern match.
    +
  • 02
    Grep for files by extension.
    Grep searches inside files. Looking for all .test.tsx files with Grep tries to match the literal string ".test.tsx" inside file contents — which is not what you want.
    Glob with **/*.test.tsx for path matching by extension or filename pattern.
    +
  • 03
    Reading the entire codebase upfront.
    Blows context, dilutes attention, costs tokens proportional to repo size. Most of what you read is irrelevant to the question at hand.
    Grep for entry points, Read targeted files, follow imports. Build understanding incrementally.
    +
  • 04
    Forcing Edit on non-unique text instead of falling back.
    Endlessly adding more context lines to make a snippet unique works for a while, then breaks on truly repetitive files. You're fighting the tool instead of switching strategies.
    When Edit fails on non-unique match, Read the full file → Write the modified version. Reliable across any file shape.
    +

Tool design is communication design. The model only knows what your descriptions tell it.
