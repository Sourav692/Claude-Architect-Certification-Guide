Question01
Code GenerationHierarchy

A senior engineer set up "team coding standards" two months ago. Today, a new hire's first PR violates every standard, even though the new hire pulled the latest main. The senior engineer insists everything is configured. Where are the rules likely stored, and what's the fix?

  • A In .claude/CLAUDE.md in the repo — the new hire needs to clone again
  • B In ~/.claude/CLAUDE.md on the senior engineer's laptop only — move them to project-level CLAUDE.md at the repo root and commit
  • C In .claude/rules/ with no glob — add a glob pattern
  • D In the project README — move them to CLAUDE.md
Correct: B

User-level configs (~/.claude/CLAUDE.md) live on one laptop and are never in version control. The new hire's clone never had them. Project-level CLAUDE.md is the right tier for team-wide rules.

A: If the rules were in the repo, the new hire would have them. C: Path globs are about file-type scoping, not the team-sharing problem. D: README isn't loaded by Claude Code as instructions.
Question02
Code GenerationPath scoping

Your codebase has React components with hook conventions, API handlers with specific error handling, and database models following a repository pattern. Test files live next to the code they test (Button.test.tsx next to Button.tsx) and are spread across many directories. You want all tests to follow the same conventions regardless of location. What's the most maintainable approach?

  • A Create rule files in .claude/rules/ with YAML frontmatter glob patterns to conditionally apply conventions based on file paths (e.g., paths: ["**/*.test.*"])
  • B Consolidate all conventions in the root CLAUDE.md file under headers for each area
  • C Create skills in .claude/skills/ for each code type and embed conventions in their SKILL.md files
  • D Place a separate CLAUDE.md file in each subdirectory containing that area's specific conventions
Correct: A

Path-scoped rules with globs apply conventions to file types regardless of directory. One file, scoped loading, no duplication.

B: Loads test rules every session even when editing non-test code — wasted tokens. C: Skills are for tasks Claude auto-invokes, not file-edit conventions. D: Tests are scattered, so directory CLAUDE.md duplicates across many directories.
Question03
Code GenerationPlan vs direct

You've been assigned to restructure your team's monolithic application into microservices. This will involve changes across dozens of files and requires decisions about service boundaries and module dependencies. Which approach should you take?

  • A Enter plan mode to explore the codebase, understand dependencies, and design an implementation approach before making changes
  • B Start with direct execution and make changes incrementally, letting the implementation reveal the natural service boundaries
  • C Use direct execution with a comprehensive upfront prompt detailing exactly how each service should be structured
  • D Begin in direct execution mode and only switch to plan mode if you encounter unexpected complexity during implementation
Correct: A

Plan mode is designed for large-scale changes with architectural decisions and multiple valid approaches — exactly what microservice restructuring is. It enables safe codebase exploration before committing to changes.

B: Risks costly rework when dependencies are discovered late. C: Assumes you know the right structure without exploring the code. D: The complexity is already known from the requirements, not something that "might emerge."
Question04
Code GenerationSlash commands

You want to create a custom /review slash command that runs your team's standard code review checklist. This command should be available to every developer when they clone or pull the repository. Where should you create this command file?

  • A In the .claude/commands/ directory in the project repository
  • B In ~/.claude/commands/ in each developer's home directory
  • C In the CLAUDE.md file at the project root, under a "commands" header
  • D In a .claude/config.json file with a commands array
Correct: A

Project-scoped commands live in .claude/commands/ in the repo. Version-controlled, automatically available after git pull.

B: User-scope is personal — teammates won't see it. C: CLAUDE.md is for instructions/context, not command definitions. D: No such configuration mechanism exists.
Question05
CI for Claude CodeNon-interactive mode

Your pipeline script runs claude "Analyze this pull request for security issues" but the job hangs indefinitely. Logs indicate Claude Code is waiting for interactive input. What's the correct approach?

  • A Set the environment variable CLAUDE_HEADLESS=true before running the command
  • B Add the --batch flag
  • C Add the -p flag: claude -p "Analyze this pull request for security issues"
  • D Redirect stdin from /dev/null: claude "..." < /dev/null
Correct: C

-p (or --print) is the documented flag for non-interactive mode. It processes the prompt, outputs to stdout, and exits — exactly what CI requires.

A & B: Reference non-existent features. D: A Unix workaround that doesn't address Claude Code's command syntax.
Question06
Code GenerationSkill output

A skill named analyze-codebase dumps thousands of lines of architectural analysis into the main session every time a developer invokes it. Subsequent turns slow down and the conversation context fills with noise. Which single change to the skill's SKILL.md frontmatter is the right fix?

  • A Add allowed-tools: [Read] to restrict the skill's tool access
  • B Add context: fork to run the skill in an isolated subagent context
  • C Add argument-hint to require a narrower scope from the developer
  • D Move the skill from .claude/skills/ to ~/.claude/skills/ for personal scope
Correct: B

context: fork isolates the skill in a subagent. Verbose output stays there; only a summary returns to the main session.

A: Restricting tools doesn't address verbosity. C: Doesn't change how output flows. D: Changing scope doesn't reduce output volume; it just removes the skill from teammates.
Question07
Code GenerationRefinement

Claude is generating date-formatted output inconsistently across calls despite a detailed natural-language specification ("format dates in a clean, professional, user-friendly way"). You've already tried adding more emphasis and constraints. What's the most effective next move?

  • A Add a stronger constraint: "ALWAYS format dates correctly and consistently"
  • B Lower the temperature on the API call
  • C Provide 2 to 3 concrete input/output examples showing the exact transformation
  • D Switch to plan mode for this task
Correct: C

Concrete I/O examples beat prose. Models generalize from the pattern; prose has irreducible interpretation variance.

A: ALL CAPS prose is still prose. B: Doesn't address ambiguity in the spec. D: Plan mode is for scope/architecture, not output formatting.
Question08
CI for Claude CodeDuplicate review comments

Your CI re-runs Claude as a PR reviewer after each new commit. Developers complain that issues already raised on prior commits keep generating new duplicate inline comments. What's the architectural fix?

  • A Disable the reviewer after the first run to avoid noise
  • B Reuse the same Claude session across all commits via --resume
  • C Cache prior findings between runs and pass them in the prompt with the instruction "Report only new or still-unaddressed issues"
  • D Switch to plan mode in CI to avoid posting comments at all
Correct: C

Pass prior findings as context with explicit deduplication instructions. Claude reports only new or unaddressed issues — clean PR feedback across commits.

A: Defeats the purpose of automated review. B: Contradicts independent-review-instances; same-session reviewer has the same blind spots. D: Plan mode isn't a CI-output mode.
Question09
Code GenerationPersonal customization

Your team uses a project-scoped skill at .claude/skills/deploy/SKILL.md. You want a personal variant that also tails logs after deploy, but you don't want to affect teammates. How should you set this up?

  • A Copy the skill to ~/.claude/skills/deploy-with-logs/ with a different name and modify the personal copy
  • B Edit .claude/skills/deploy/SKILL.md in place and avoid committing the change
  • C Add a personal flag to the project skill via argument-hint
  • D Copy the skill to ~/.claude/skills/deploy/ with the same name to override the team version
Correct: A

Personal scope (~/.claude/) plus a different name keeps both versions available without collision or accidental commits.

B: The change can be reverted on the next pull, or accidentally committed. C: argument-hint prompts for input; it's not a customization mechanism. D: Same name in personal scope can shadow the team version unpredictably and breaks for teammates if it leaks back.
Question10
CI for Claude CodeTest generation noise

Your CI uses Claude to generate tests for new code in PRs. Developers report that generated tests frequently duplicate scenarios already covered by the existing test suite, polluting the suite with low-value tests. What's the most effective fix?

  • A Increase the model's reasoning budget so it considers existing tests more carefully
  • B Provide existing test files in context and document testing standards, valuable test criteria, and available fixtures in CLAUDE.md
  • C Run test generation in plan mode so the developer reviews each test before commit
  • D Switch the test framework so Claude has fewer existing tests to consider
Correct: B

Two changes work together: existing tests in context tell Claude what's already covered, and CLAUDE.md defines what counts as a valuable test (real bug coverage, not coverage padding). The combination cuts duplicate-and-low-value test generation.

A: Reasoning budget doesn't help when the existing tests aren't even visible. C: Plan mode is about exploration, not output filtering. D: Switching frameworks is unrelated to the noise problem.
