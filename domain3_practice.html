3.1 CLAUDE.md hierarchy 2 q
Q01 Task 3.1The new-team-member trap

A senior engineer says "I configured all our team's coding standards in Claude Code two months ago." A new hire's first PR violates every standard. Where are the rules likely stored, and what's the fix?

Model answer

In ~/.claude/CLAUDE.md on the senior engineer's laptop only. User-level configs aren't shared via git, so the new hire's clone never had them. Fix: move the standards to project-level CLAUDE.md at the repo root and commit. Reserve ~/.claude/CLAUDE.md for personal preferences only.

Q02 Task 3.1Debugging command

You added a new rule to CLAUDE.md yesterday, but Claude is still ignoring it in this session. What's the FIRST command you run to diagnose?

Model answer

/memory. It shows exactly which CLAUDE.md files were loaded into the current session and in what order. If your file isn't in the list, the issue is location (wrong tier, wrong path) or import wiring. Distractors to avoid: /config and /loaded aren't real commands.

3.2 Custom commands & skills 2 q
Q03 Task 3.2Verbose skill output

A skill named analyze-codebase dumps thousands of lines of analysis into your main session every time you invoke it. Subsequent turns are slow and your context is full of noise. Which single frontmatter change fixes this?

Model answer

Add context: fork to the skill's frontmatter. That runs the skill in an isolated subagent, so the verbose output stays in the subagent's context. Only the summary returns to your main session. allowed-tools would restrict tools but doesn't solve verbosity; prompt instructions to "be concise" are unreliable.

Q04 Task 3.2Personal customization

Your team has a project-scoped skill .claude/skills/deploy/SKILL.md. You want a personal variant that also tails logs. How do you add your variant without affecting teammates?

Model answer

Copy the skill to ~/.claude/skills/<different-name>/SKILL.md (e.g., deploy-with-logs) and modify it there. Two requirements: (1) personal scope (under ~/.claude/, not in the repo) and (2) different name to avoid shadowing or collision with the team version. Editing the team's file in-place would either commit your preference to git or get reverted on the next pull.

3.3 Path-specific rules 2 q
Q05 Task 3.3Scattered file types

Your test files are co-located with the code they test (Button.tsx next to Button.test.tsx), spread across many directories. You want all tests to follow the same conventions. Which approach is most maintainable?

Model answer

A path-scoped rule: .claude/rules/testing.md with YAML frontmatter paths: ["**/*.test.*"]. One file, glob-matches every test file across the codebase, loads only when editing one. Directory-level CLAUDE.md would force you to duplicate the file in every directory containing tests; root CLAUDE.md wastes tokens loading test rules during non-test work.

Q06 Task 3.3Token efficiency

Why does putting test conventions in root CLAUDE.md hurt token efficiency, even though it "works"?

Model answer

Root CLAUDE.md loads every session, regardless of what files Claude is editing. That means test rules are in context when Claude is editing API handlers, infra, docs, anything else — wasted tokens and diluted attention. Path-scoped rules load only when matching files are being edited. With many topic files, the cumulative savings are significant.

3.4 Plan mode vs direct execution 2 q
Q07 Task 3.4Mode selection

You're tasked with migrating from one ORM to another, affecting roughly 60 query call sites across the codebase. Plan mode or direct execution, and why?

Model answer

Plan mode, then transition to direct execution after approval (the hybrid pattern). The reasoning: large-scale change (60 sites), architectural implications (ORM-specific features may not translate cleanly), multiple valid approaches (which queries to migrate first, how to handle incompatible features). Plan mode lets Claude explore dependencies and surface constraints before commit. "Start direct, switch later" is wrong — the complexity is already known from the requirements.

Q08 Task 3.4Explore subagent

You ask Claude to "trace how authentication flows through this codebase" in an unfamiliar 200-file repo. Should you use the Explore subagent? Why?

Model answer

Yes — verbose discovery across many files is exactly the Explore use case. Without Explore, the content of the 30+ files Claude reads ends up in your main context, exhausting it before you can act on the understanding. With Explore, the subagent reads them and returns a summary. You wouldn't reach for Explore on a 2-file trace where you'll need the raw content in subsequent turns.

3.5 Iterative refinement 2 q
Q09 Task 3.5Prose isn't converging

Claude's date-formatting output is inconsistent across calls despite a detailed natural-language specification. You've already added more emphasis and constraints. What's the most effective next move?

Model answer

Provide 2 to 3 concrete input/output examples. Prose has irreducible interpretation variance; concrete I/O pairs eliminate the ambiguity. The model generalizes from the pattern. Stronger prose, ALL CAPS, or "ALWAYS DO X" don't address the root cause — they just make the prompt longer.

Q10 Task 3.5Single vs sequential

You discover three independent bugs in three different files. None of the bugs share state or calculations. Single message with all three, or sequential? Why?

Model answer

Sequential. Independent issues don't interact, so joint reasoning adds no value. Sequential keeps each fix small, verifiable, and traceable — if a fix introduces a regression, you can bisect cleanly. Reserve single-message refinement for issues that share state (e.g., tax/discount/shipping all flowing through subtotal) where fixing one in isolation can unwind another.

3.6 CI/CD integration 2 q
Q11 Task 3.6CI hang

Your CI job runs claude "Analyze this PR" and hangs indefinitely. What flag fixes it, and what's the underlying mechanism?

Model answer

-p (or --print). Without it, Claude Code runs in interactive mode, waiting for stdin that never arrives. With -p, Claude processes the prompt, writes to stdout, exits. Distractor answers like --batch, CLAUDE_HEADLESS=true, or redirecting from /dev/null are inventions or workarounds that don't address the actual mechanism.

Q12 Task 3.6Duplicate review comments

Re-running the Claude reviewer after each new commit produces duplicate inline comments on issues already raised on prior commits. Developers complain. What's the architectural fix?

Model answer

Cache prior findings between runs and pass them in the prompt with the explicit instruction "Report ONLY new or still-unaddressed issues." Claude deduplicates against the prior list. Don't try to "reuse the same session via --resume" — that contradicts the independent-review-instances principle (the session that generated the code is a worse reviewer).
