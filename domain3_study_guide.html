03.1
Task statement 3.1 · CLAUDE.md hierarchy

Three levels. One trap.

The exam tests which file holds the rule. User-level configs aren't shared, project-level configs are, and directory-level configs scope to a subtree. If you can recognize the new-team-member trap and know /memory, you'll get every Task 3.1 question right.

What CLAUDE.md actually does

CLAUDE.md is a markdown file that Claude Code reads automatically at the start of every session. There are three locations Claude looks in, with different scopes and sharing semantics.

The three levels

  • ~/.claude/CLAUDE.md — user-level. On your machine only. Never shared. Personal preferences live here.
  • CLAUDE.md at repo root (or .claude/CLAUDE.md) — project-level. In git. Every teammate gets it on git pull. The default for team rules.
  • subdir/CLAUDE.md — directory-level. Loads only when Claude is working in that subtree. For conventions bounded to one directory.

All three load together when applicable. Lower levels override higher ones, so a directory rule beats a project rule beats a user rule.

Hover any tier to see scope and sharing semantics. The trap is at the top — user-level rules look like they work, but only for you.

The new-team-member trap

A senior engineer configures ~/.claude/CLAUDE.md with "always use pytest, never use print(), all DB calls go through the repository pattern." Their generated code looks great. A new hire joins, clones the repo, and Claude generates code that uses print() and bypasses the repository.

The senior dev says "but I configured the rules!" — they configured them on their machine. The rules were never in version control. This is the canonical exam scenario for Task 3.1. The fix: move them to project-level CLAUDE.md and commit.

@import and .claude/rules/ for modularity

Stop building one giant CLAUDE.md. Two patterns scale better:

@import — modular CLAUDE.md
Selective imports per package

The root CLAUDE.md imports topic files. Each subpackage's CLAUDE.md can import only what's relevant to that package's domain. Maintainers control what loads.

# CLAUDE.md (project root) # Universal team standards - TypeScript strict mode - Conventional commits @import .claude/rules/testing.md @import .claude/rules/api-conventions.md @import .claude/rules/deployment.md
.claude/rules/ — topic-specific files
Splitting a monolith into focused files

Rather than one large CLAUDE.md, split rules into single-purpose files: testing.md, deployment.md, api-conventions.md. Smaller files are easier to review in PRs, and they become path-scopable (preview of Task 3.3).

.claude/ └── rules/ ├── testing.md ├── api-conventions.md └── deployment.md

/memory — the debugging command

Inside a Claude Code session, run /memory. It shows exactly which CLAUDE.md files were loaded and in what order. Reach for this whenever:

  • "Why is Claude ignoring my rule?" → /memory shows your file isn't loaded.
  • "Joe's session behaves differently than mine" → compare /memory outputs across machines.
  • "I added a rule but no effect" → maybe you added it to the wrong tier.

This is the first tool to reach for when configuration behavior is inconsistent. Distractor answers like /config or /loaded aren't real commands.

    Use a path-scoped rule (Task 3.3) with a glob pattern. One file, applies everywhere the glob matches.

03.2
Task statement 3.2 · Custom commands and skills

Two mechanisms. Same directory. Different roles.

Commands are explicit — the user types /review. Skills are auto-invoked when Claude detects a task match. Both have project vs personal scoping. The exam tests where each lives, when to fork, and which frontmatter field solves which problem.

Commands vs skills — the orientation

Both live under .claude/. Both can be project-scoped (in git, shared) or personal-scoped (your machine only). The mental split:

  • Slash commands live in .claude/commands/<name>.md. The user invokes them explicitly: /review, /deploy-check. Predictable, named workflows.
  • Skills live in .claude/skills/<name>/SKILL.md. Claude auto-invokes them when the task matches the skill's description. On-demand, not user-typed.
  • Project scope = .claude/ in the repo, in git, every teammate gets it.
  • Personal scope = ~/.claude/ on your machine only.

Three frontmatter fields, three different problems. Hover any field to see the exam scenario it solves.

When context: fork pays off

You build a skill that scans a monorepo for outdated dependencies. Without context: fork, Claude reads dozens of package.json files and dumps thousands of lines of audit output into the main session. Your context is now half-full of stuff you don't need. Subsequent messages are slower and more expensive.

With context: fork, the subagent does the scan in isolation and returns a summary like "23 outdated, 4 critical CVEs, top fix: upgrade lodash to 4.17.21". Main session stays clean. The same pattern applies to brainstorming skills, codebase analysis, exploratory research — anything that's verbose by nature.

Without context: fork
Verbose output pollutes the main session

3000+ lines of audit data live in your conversation history. Every subsequent turn pays the token cost. Claude's attention dilutes across irrelevant noise.

With context: fork
Summary returns; raw output stays in the subagent

Main session sees only the conclusions. Token cost is bounded. Subsequent turns are fast and focused.

Where things live — at a glance

Need Path Shared with team?
/review command for everyone.claude/commands/review.mdYes — via git
Personal /deploy-with-logs~/.claude/commands/deploy-with-logs.mdNo — your laptop
Skill the team auto-invokes.claude/skills/audit-deps/SKILL.mdYes — via git
Personal variant of a team skill~/.claude/skills/audit-deps-mine/SKILL.mdNo — different name avoids collision

Personal customization rule: when you want a tweaked version of the team's skill or command, copy it to ~/.claude/... with a different name. Same name in personal scope can shadow the team version unpredictably.

Anti-patterns & exam traps

  • 01
    Creating team commands in ~/.claude/commands/.
    User-scope commands are private to your machine. Teammates won't see them after git pull because they were never in git.
    Project-scoped commands live in .claude/commands/ at the repo root. Commit them.
    +
  • 02
    Verbose skills polluting the main session — fixing it with prompt instructions.
    Telling the skill "be concise" doesn't change the fact that its outputs land in the main conversation. The architectural fix isn't a prompt — it's isolation.
    Add context: fork to the skill frontmatter. Output stays in the subagent; you get back the summary.
    +
  • 03
    Editing the team's skill file in-place to add personal tweaks.
    Now your changes are in the team's repo. Teammates inherit your preferences, or your changes get reverted on the next pull.
    Copy the skill to ~/.claude/skills/<new-name>/. Use a different name to coexist with the team version.
    +
  • 04
    Using a skill where CLAUDE.md is the right tool — or vice versa.
    CLAUDE.md = always-loaded universal context. Skills = on-demand tasks Claude invokes when matched. They're not interchangeable.
    Universal team standards → CLAUDE.md. Named workflows the user runs explicitly → commands. On-demand task patterns → skills.

03.3
Task statement 3.3 · Path-specific rules

Conventions that follow file types, not directories.

When test files are scattered through the codebase next to the code they test, you can't put a CLAUDE.md in every directory. Path-scoped rules with glob patterns load only when matching files are being edited. Token efficiency and the canonical "scattered tests" exam scenario.

The mechanism

Inside .claude/rules/, files have YAML frontmatter that specifies a glob pattern. Claude Code loads the rule only when editing a file matching the glob. If you're editing source code and the rule's pattern matches only test files, the rule doesn't load — its tokens stay out of context.

# .claude/rules/testing.md --- paths: ["**/*.test.tsx", "**/*.test.ts"] --- # Test conventions - All tests use Vitest. describe/it. No snapshots. - Mock with vi.mock at the top of the file. - Reuse fixtures in tests/fixtures/ before creating new ones.
Figure 3.3 · Path rules vs directory CLAUDE.md — when tests are scattered
Hover either side. Same problem, two architectures — the right-hand approach is the canonical exam answer for scattered file types.

Token efficiency

Every rule loaded into a session consumes tokens. Imagine 12 topic-specific rule files, all loading every session — that's a lot of context spent on conventions Claude doesn't need at that moment. Path-scoping means a rule lands in context only when relevant. Multiple rules can each load conditionally, keeping the session lean.

When directory-level CLAUDE.md is still the right tool

Path-scoping isn't always better. The decision rule:

Directory-level CLAUDE.md
When the convention is bounded to a subtree

"Everything under infra/terraform/ uses these naming standards" — a single subtree, single CLAUDE.md, no globs needed. The rule applies whenever Claude works in that directory.

Path-scoped rule with glob
When the convention follows a file type spread across the codebase

"All *.test.* files use Vitest, regardless of where they live" — tests are scattered, so directory-level would force duplication. One path-scoped rule catches them all.

!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Test files are scattered — put test conventions in root CLAUDE.md."
    It works, but every session loads test rules even when Claude is editing source code, infra, docs, or anything else. Tokens wasted on irrelevant context, attention diluted.
    Path-scoped rule: .claude/rules/testing.md with paths: ["**/*.test.*"]. Loads only when editing a test.
    +
  • 02
    "Use a skill for test conventions."
    Skills are for tasks Claude auto-invokes (audits, brainstorms, scans). They're not the right vehicle for "always follow these rules when editing this file type."
    Conventions that follow file edits → path-scoped rules. Skills are for executable workflows.
    +
  • 03
    Putting a CLAUDE.md in every directory that contains tests.
    Duplication. Drift. When test conventions change, you update N files. Some get forgotten and conventions diverge.
    One path-scoped rule with a glob covers every test file across the entire codebase.
    +
  • 04
    Using path-scoping when the convention is genuinely directory-bounded.
    Over-engineering. If "everything under infra/terraform/" gets the same rules, a directory-level CLAUDE.md is simpler and clearer.
    Single subtree → directory-level. File type spread across subtrees → path-scoped. Pick the simpler tool when both work.
    +
03.4
Task statement 3.4 · Plan mode vs direct execution

Think before changing — but only when changing is hard.

Plan mode explores and designs without making edits. Direct execution edits immediately. The exam tests whether you can recognize "architectural complexity already known from the requirements" — that's plan mode, not "switch later if it gets hard."

The two modes — and what each is for

  • Direct execution — Claude reads, edits, and runs commands immediately. Default for changes with clear scope.
  • Plan mode — Claude explores the codebase, designs an approach, and presents a written plan without making any changes. You review and approve before implementation.
  • The Explore subagent — a specialized subagent for verbose discovery (reading dozens of files, tracing dependencies). Returns a summary to the main session, preserving context.
Figure 3.4 · The decision tree
Hover any node to see when that mode applies. The hybrid path at the bottom is the production reality for big migrations.

The Explore subagent

Same idea as context: fork for skills, but for ad-hoc exploration. When you ask Claude to "trace how authentication flows through this codebase," Claude needs to read 30 files. Without the Explore subagent, those 30 files' content lives in your main context. With Explore, the subagent reads them and returns a summary like a 100-line architectural overview.

When NOT to reach for Explore: simple two-file traces, work where you'll need the raw file contents in subsequent turns. It's a tool for verbose discovery, not for every task.

The hybrid pattern (production reality)

Most non-trivial production work follows this loop:

  • Plan mode → understand the codebase, design the approach, identify risks.
  • Review the plan, push back where needed, approve.
  • Direct execution → implement the approved plan step by step.
  • Optional: Explore subagent for tangents that would otherwise blow context.
!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Start in direct execution; switch to plan mode if it gets complicated."
    Classic exam trap. The complexity is already known from the requirements (e.g., "restructure the monolith into microservices, dozens of files"). Waiting to discover it means rework, partial edits, and a half-broken codebase.
    If the requirement names architectural change, multi-file scope, or migrations — plan mode from the start.
    +
  • 02
    Plan mode for every task, including obvious one-line fixes.
    Ceremony. A clear stack trace and a single-file fix don't need a written plan — that's just slowing yourself down.
    Direct execution for well-scoped changes. Plan mode for complexity, architecture, or scope.
    +
  • 03
    Using the Explore subagent on every task to "save context."
    Explore is for verbose discovery — reading many files and returning a summary. On a two-file trace, you'd still need the raw content in subsequent turns; the summary doesn't help.
    Reach for Explore when discovery would consume serious context. Otherwise read directly.
    +
  • 04
    Comprehensive upfront prompt detailing exactly how to restructure a system.
    Assumes you already know the right structure without exploring the code. The whole point of plan mode is that you discover constraints during exploration.
    Plan mode lets Claude surface those constraints before you commit to an approach. Read the plan, then commit.
    +
03.5
Task statement 3.5 · Iterative refinement

When prose fails, examples don't.

Four refinement techniques, each with a specific use case. The exam tests recognition: prose-isn't-working → concrete examples; unfamiliar domain → interview pattern; interacting bugs → single message; independent bugs → sequential.

Concrete examples beat prose

The single most effective refinement move. When Claude misinterprets a vague specification, more prose rarely helps — the model interprets prose unevenly across calls. Two or three concrete input/output pairs eliminate the ambiguity.

Prose specification — interpreted unevenly
"Format dates more user-friendly"

What's "user-friendly"? Long-form? Short? With time? Without? Claude will pick something, and the choice will vary across calls. More prose ("be concise, professional, etc.") doesn't pin it down.

Concrete I/O pairs — unambiguous
Three examples that fix the format
input: "2024-03-15T10:30:00Z" output: "Mar 15, 2024" input: "2024-12-31T23:59:59Z" output: "Dec 31, 2024" input: null output: "—"

Production rule: if you've described the same requirement in prose more than twice without convergence, you don't need more prose — you need 2 to 3 I/O examples.

Figure 3.5 · Four refinement techniques
Four techniques, four triggers. Hover any quadrant to see when to reach for it.

Single message vs sequential — the trade-off that matters

The decision depends on whether issues interact. Independent issues are easier to fix sequentially: each fix is small, verifiable, and traceable. Interacting issues need joint reasoning — fixing them sequentially means the second fix may unwind the first.

Sequential fits
Three independent bugs in three files

Bug 1: null email crashes a migration. Bug 2: duplicate IDs throw. Bug 3: timezone conversion wrong. None share state. Fix each in turn. Bisecting is trivial if a fix introduces a regression.

Single message fits
Three interacting calculation bugs

Tax wrong, discount wrong, shipping wrong — and all flow through subtotal. Fixing tax in isolation may re-derive discount incorrectly. Send all three with their I/O examples in one message; Claude reasons jointly.

!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Make the prose more detailed and emphatic" when output is inconsistent.
    Prose interpretation has irreducible variance. ALL CAPS and "ALWAYS DO X" don't fix that — they just make the prompt longer.
    Provide 2 to 3 concrete input/output examples. Models generalize from patterns reliably.
    +
  • 02
    Sending three interacting bugs sequentially.
    Fix #1 reasons about its calculation in isolation. Fix #2 may re-derive an upstream value differently, breaking #1. You're playing whack-a-mole.
    Single message with all three issues, their I/O examples, and the note that they interact through shared state.
    +
  • 03
    Sending three INDEPENDENT bugs in one mega-prompt.
    Wastes attention. If a fix introduces a regression, you can't bisect. The model spends tokens reasoning about three unrelated changes simultaneously.
    Sequential fixes for independent issues. Each fix verified, each diff small.
    +
  • 04
    Implementing in unfamiliar territory without an interview round.
    You don't know what you don't know. Claude implements against the surface request and misses important constraints (idempotency, consistency model, partial failure handling).
    "Before implementing, ask me 5 questions about my requirements." Then code.
    +
03.6
Task statement 3.6 · CI/CD integration

Non-interactive mode, structured output, independent reviewers.

The most-tested fact: -p is the flag for non-interactive mode. Beyond that — JSON output for machine parsing, prior-findings context to deduplicate review comments, and independent review instances because self-review has the same blind spots.

The -p flag — the canonical exam question

Without -p (or --print), Claude Code runs interactively, waiting for stdin. Your CI job hangs forever. With -p, Claude processes the prompt, writes the result to stdout, exits.

# The fix for "CI job hangs indefinitely": claude -p "Review this PR for security issues"

The exam will dangle plausible-sounding distractors: --batch, CLAUDE_HEADLESS=true, redirecting stdin from /dev/null. None of those exist or address the mechanism. -p is the documented non-interactive flag. Memorize it.

Figure 3.6 · Claude Code in a CI pipeline
Hover any node. The two feedback loops at the bottom — CLAUDE.md context and prior-findings cache — are the noise-reduction levers.

Independent review instances

The Claude session that generated code is a worse reviewer than a fresh session. Same context, same blind spots, same assumptions. It will skim past the bug it just introduced because it already justified the choice. In CI this is automatic — review jobs spawn fresh sessions — but the exam asks why it matters: session context isolation produces better review than self-review.

Incremental review context

When a PR gets new commits, you re-run review. Without context, Claude re-flags every issue from the prior review — duplicate comments, developer frustration, eventually they ignore the bot. Fix:

claude -p "Review this diff per CLAUDE.md severity rules. Prior findings already reported on this PR: [ ... cached findings JSON ... ] Report ONLY new or still-unaddressed issues." \ --output-format json \ --json-schema review-schema.json

Cache the findings between runs. Pass them as context. Claude deduplicates.

CLAUDE.md as the CI noise-reduction lever

CI-invoked Claude still reads project CLAUDE.md. Use it to specify:

  • Severity definitions — what counts as critical vs nit, with concrete code examples for each.
  • What to skip — "ignore Prettier-handled style issues; ignore minor naming preferences."
  • Testing standards — what makes a valuable test (real bug coverage, not coverage padding).
  • Available fixtures — so generated tests reuse them instead of inventing duplicates.

This is how you get from 50 low-signal CI comments per PR to 5 high-signal ones.

  • 01
    "Job hangs forever — set CLAUDE_HEADLESS=true" or "add --batch".
    Those don't exist. Distractor answers that sound plausible because of conventions in other tools. Claude Code's mechanism is different.
    -p (or --print). It's the documented non-interactive flag. Memorize it.

    Same Claude session generates code AND reviews it.

    Generated tests duplicate existing coverage.
    Claude doesn't know what's already tested. Without context, it generates tests for behaviors already covered, polluting the suite.
    Provide existing test files in context. Document available fixtures and "what makes a valuable test" in CLAUDE.md.
