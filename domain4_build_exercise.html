Build a production extraction tool.

One exercise that wires every Domain 4 concept into a single working system — schema, few-shot, forced tool use, semantic validators, bounded retry, batch submission, and an independent reviewer. Try it before revealing the solution.

Exercise

The brief.

Build an extraction tool that processes 10 invoice documents end-to-end with all six Domain 4 concepts integrated. Log each document's outcome: pass, passed-on-retry, or human-review.

What you're operationalizing.

Each of the six task statements patches a specific failure mode. Wire them in this order — the order is the architecture.

4.1
Explicit criteria

Categorical inclusion + exclusion in the prompt — what to extract, what to skip.

4.2
Few-shot

2-3 worked examples with reasoning. One must demonstrate null-return for missing data.

4.3
Tool-use schema

JSON schema with required, nullable, "unclear" enum, "other" + detail. Forced selection.

4.4
Validators + retry

Pydantic semantic check (calculated_total vs stated_total). Bounded retry with error.

4.5
Batch (stretch)

Wrap the 10 docs into a Message Batches submission with custom_id correlation.

4.6
Independent review (stretch)

Second instance with no prior context flags suspicious values with confidence.

Specification

Required deliverables.

All six items below must be present in your solution. Stretch goals are optional — build them if you want full coverage of Tasks 4.5 and 4.6.

  1. JSON schema with required, optional, and nullable fields; an enum that includes "unclear" and "other" + a sibling detail string.
  2. 2-3 few-shot examples in the system prompt — at least one demonstrating null-return when source data is genuinely absent.
  3. tool_choice forced selection — single extractor, must always run.
  4. Pydantic validation with a semantic check: calculated_total vs stated_total. Disagreement raises a validation error.
  5. Validation-retry loop bounded at 2 retries. The retry message must include the document, the failed extraction, and the specific validator error.
  6. Process 10 documents and log each outcome: pass, passed-on-retry, or human-review.

Stretch goals.

  1. detected_pattern field on findings to enable false-positive analysis by pattern cluster.
  2. Batch submission wrapping the 10 documents with custom_id for correlation back to source docs.
  3. Independent reviewer instance that examines the extracted output with a fresh context, attaches a confidence label, and routes low-confidence to a human-review queue.

01
Pydantic models with semantic validator
Task 4.3 + 4.4

Pydantic gives you both type safety and a place to put cross-field semantic checks. The totals_must_match validator is the semantic gate — it fails when line items don't sum to the stated total, even though the tool_use schema would accept any numbers. 

from pydantic import BaseModel, ValidationError, field_validator
from typing import Optional, List, Literal

class LineItem(BaseModel):
    description: str
    amount: float

class ExtractionResult(BaseModel):
    vendor_name: str
    vendor_type: Literal["supplier", "service", "other", "unclear"]
    vendor_type_other: Optional[str] = None     # "other" + detail
    currency: Literal["USD", "EUR", "GBP", "unclear"]
    stated_total: Optional[float]                  # nullable
    calculated_total: float
    line_items: List[LineItem]

    @field_validator('calculated_total')
    @classmethod
    def totals_must_match(cls, v, info):
        items = info.data.get('line_items', [])
        items_sum = sum(li.amount for li in items)

        if abs(v - items_sum) > 0.01:
            raise ValueError(
                f"calculated_total {v} != sum(line_items) {items_sum}"
            )

        stated = info.data.get('stated_total')
        if stated is not None and abs(stated - items_sum) > 0.01:
            raise ValueError(
                f"stated_total {stated} != sum(line_items) {items_sum}"
            )
        return v
Why this works
The schema (next stage) catches syntactic errors — wrong types, missing required fields, bad enums. This validator catches semantic errors — numbers that pass type-checking but don't add up. Both layers are necessary.
02
JSON schema for tool_use
Task 4.3

Three production patterns are baked in: nullable on stated_total (some quotes have no total), "unclear" in both enums (somewhere to land for ambiguous data), and "other" + detail via the vendor_type_other sibling field. 

extract_tool = {
    "name": "extract_invoice",
    "description": "Extract structured data from an invoice",
    "input_schema": {
        "type": "object",
        "properties": {
            "vendor_name": {"type": "string"},
            "vendor_type": {
                "type": "string",
                "enum": ["supplier", "service", "other", "unclear"]
            },
            "vendor_type_other": {"type": ["string", "null"]},
            "currency": {
                "type": "string",
                "enum": ["USD", "EUR", "GBP", "unclear"]
            },
            "stated_total": {"type": ["number", "null"]},  # nullable
            "calculated_total": {"type": "number"},
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "amount": {"type": "number"}
                    },
                    "required": ["description", "amount"]
                }
            }
        },
        "required": [
            "vendor_name", "vendor_type", "currency",
            "calculated_total", "line_items"
        ]
        # stated_total NOT required - may be missing on quotes
    }
}
Pattern check
Required + non-nullable on every field is the trap that forces fabrication. Here, stated_total is omitted from required AND nullable — so the model can honestly return null when a quote has no total, instead of inventing one.
03
System prompt with criteria + few-shot
Task 4.1 + 4.2

Three examples covering the failure surface: a standard invoice (sanity check), a quote with no totals (teaches null-return), and a single-line item invoice (teaches that line_items can be derived from billing context). 

SYSTEM_PROMPT = """Extract structured data from invoices.

Rules:
- Extract amounts as numbers (not strings)
- Use "unclear" for currency only when no symbol or
  code is present anywhere in the document
- Return null for stated_total ONLY if no total
  appears in the document
- Do NOT fabricate values to fill required fields

Examples:

INPUT: "Acme Corp - 3 widgets @ $10 = $30, total $30 USD"
OUTPUT: vendor_name="Acme Corp", vendor_type="supplier",
  currency="USD", stated_total=30.00, calculated_total=30.00,
  line_items=[{"description": "3 widgets", "amount": 30.00}]
REASONING: Standard invoice; sum matches stated total.

INPUT: "Quote from BetaServices for consulting work, no totals listed"
OUTPUT: vendor_name="BetaServices", vendor_type="service",
  currency="unclear", stated_total=null, calculated_total=0.00,
  line_items=[]
REASONING: Quote with no amounts. Currency unclear, totals null.
  Don't fabricate.

INPUT: "Gamma LLC, services rendered, billing: 100 EUR"
OUTPUT: vendor_name="Gamma LLC", vendor_type="service",
  currency="EUR", stated_total=100.00, calculated_total=100.00,
  line_items=[{"description": "services rendered", "amount": 100.00}]
REASONING: Single line item; description from billing context.
"""
Example design
The middle example is the most important — it teaches null-return for absent data. Without it, the model fabricates totals. This single example dramatically reduces hallucination.
04
Bounded retry with error feedback
Task 4.4

Two retries max. Each retry message includes the failed extraction AND the specific Pydantic error. The instruction "return null if data is genuinely absent" is critical — without it, the model retries with another fabricated value. 

import anthropic
client = anthropic.Anthropic()

def extract(document: str, max_retries: int = 2):
    """Returns (result, attempts_used). result is None if exhausted."""
    messages = [{
        "role": "user",
        "content": f"Extract from this invoice:\n\n{document}"
    }]

    for attempt in range(max_retries + 1):
        resp = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=2048,
            system=SYSTEM_PROMPT,
            tools=[extract_tool],
            tool_choice={"type": "tool", "name": "extract_invoice"},
            messages=messages
        )
        raw = resp.content[0].input

        try:
            return ExtractionResult(**raw), attempt
        except ValidationError as e:
            if attempt == max_retries:
                return None, attempt    # exhausted

            messages.append({"role": "assistant", "content": resp.content})
            messages.append({
                "role": "user",
                "content": (
                    f"Validation failed: {e}\n\n"
                    f"Re-examine the document and produce a corrected "
                    f"extraction. If data is genuinely absent, return "
                    f"null rather than guessing."
                )
            })
Why bounded
Retry helps for fixable cases — wrong type, swapped fields, arithmetic mistakes. Retry can't help when data is absent. Bounding at 2-3 stops you burning cost on the unfixable; routing to human review handles them properly.
05
Process 10 documents and log outcomes
Task 4.4

Three outcome buckets: pass (first try), retry_pass (succeeded after retry), human_review (exhausted). Logging outcomes is what lets you actually see the retry mechanism's value in production. 

documents = [...]   # list of 10 invoice text strings
results = {"pass": 0, "retry_pass": 0, "human_review": 0}
log_lines = []

for i, doc in enumerate(documents):
    result, attempts = extract(doc)

    if result is None:
        results["human_review"] += 1
        log_lines.append(f"Doc {i:02d}: HUMAN_REVIEW after {attempts} retries")
    elif attempts == 0:
        results["pass"] += 1
        log_lines.append(f"Doc {i:02d}: PASS")
    else:
        results["retry_pass"] += 1
        log_lines.append(f"Doc {i:02d}: PASSED on retry {attempts}")

for line in log_lines:
    print(line)
print(f"\nFinal: {results}")

06
Stretch: batch submission with custom_id
Task 4.5

Wrap the 10 docs into a single batch submission for 50% cost savings — only appropriate when this is non-blocking work. Note: the batch cannot contain the validation-retry loop (no multi-turn within a batch request); retry happens after results return. 

import time

batch_requests = [
    {
        "custom_id": f"doc_{i:03d}",
        "params": {
            "model": "claude-sonnet-4-5",
            "max_tokens": 2048,
            "system": SYSTEM_PROMPT,
            "tools": [extract_tool],
            "tool_choice": {"type": "tool", "name": "extract_invoice"},
            "messages": [{"role": "user", "content": f"Extract:\n\n{doc}"}]
        }
    }
    for i, doc in enumerate(documents)
]

batch = client.messages.batches.create(requests=batch_requests)

# Poll until completion
while True:
    status = client.messages.batches.retrieve(batch.id)
    if status.processing_status == "ended":
        break
    time.sleep(60)

# Validate after results return - retry failures separately
needs_retry = []
for r in client.messages.batches.results(batch.id):
    if r.result.type != "succeeded":
        needs_retry.append(r.custom_id)
        continue
    raw = r.result.message.content[0].input
    try:
        result = ExtractionResult(**raw)
    except ValidationError:
        needs_retry.append(r.custom_id)

# Resubmit ONLY failures - never re-run the full batch
Constraint to remember
Batch requests are single-turn. You cannot embed the validation-retry conversation inside a batch request. Validate after results return; retry failures via sync calls or a follow-up batch.
07
Stretch: independent reviewer instance
Task 4.6

A fresh Claude instance with no prior reasoning context reviews the extracted output and emits a confidence label. Low-confidence results route to a human queue. Self-review fails because the original instance defends its work — an independent instance has nothing to defend. 

def independent_review(document: str, extraction: ExtractionResult):
    """Fresh instance reviews extraction with no prior context."""

    review_prompt = f"""Original document:
{document}

Extracted data:
{extraction.model_dump_json(indent=2)}

Review the extraction for accuracy. Output JSON:
{{
  "confidence": "high" | "medium" | "low",
  "concerns": ["specific concern 1", ...],
  "should_route_to_human": boolean
}}

Flag concerns for: numerical mismatches, vendor name
ambiguity, currency confusion, items that look hallucinated.
"""

    # Note: NEW client.messages.create call - fresh context
    resp = client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=1024,
        messages=[{"role": "user", "content": review_prompt}]
    )

    return parse_review(resp.content[0].text)


# Routing logic
for i, doc in enumerate(documents):
    extraction, _ = extract(doc)
    if extraction is None:
        route_to_human_queue(i, doc, reason="extraction_failed")
        continue

    review = independent_review(doc, extraction)
    if review["confidence"] == "high":
        auto_accept(extraction)
    else:
        route_to_human_queue(i, doc, reason=review["concerns"])
Calibration matters
Confidence labels are only useful as a routing signal once calibrated against a labeled validation set. Track accuracy per confidence bucket. Without calibration, the model's "high" might still be 60% correct — and you'll auto-accept errors.

Stretch: detected_pattern field
Task 4.4

Add a per-line-item field that records which extraction pattern the model used. When errors cluster (e.g., "all dismissed values used the tax_inferred_from_percentage pattern") you have a concrete prompt fix instead of a generic "improve accuracy" task. 

# Extend the schema
"line_items": {
    "type": "array",
    "items": {
        "type": "object",
        "properties": {
            "description": {"type": "string"},
            "amount": {"type": "number"},
            "detected_pattern": {
                "type": "string",
                "enum": [
                    "explicit_amount",         # "$100"
                    "unit_price_x_quantity",    # "3 @ $10"
                    "tax_inferred_from_pct",    # "VAT @ 20%"
                    "derived_from_total",       # total - other items
                    "single_line_billing"       # "billing: $X"
                ]
            }
        },
        "required": ["description", "amount", "detected_pattern"]
    }
}

from collections import Counter

dismissed_patterns = Counter()
for dismissal in human_review_log:

Pattern names beat confidence scores
Confidence scores tell you the model felt unsure. Pattern names tell you which kind of input caused the failure. Only the latter enables a targeted prompt fix.

Full integrated script.

Stages 1-5 wired together as a single runnable file. Stretch goals (6-8) can be added on top — see each stage above for the additions. 

"""
Domain 4 Build Exercise - reference solution.
Integrates Tasks 4.1, 4.2, 4.3, 4.4 in a single extraction pipeline.
"""
import anthropic
from pydantic import BaseModel, ValidationError, field_validator
from typing import Optional, List, Literal

client = anthropic.Anthropic()

# ---------- 1. PYDANTIC MODELS WITH SEMANTIC VALIDATOR ----------
class LineItem(BaseModel):
    description: str
    amount: float

class ExtractionResult(BaseModel):
    vendor_name: str
    vendor_type: Literal["supplier", "service", "other", "unclear"]
    vendor_type_other: Optional[str] = None
    currency: Literal["USD", "EUR", "GBP", "unclear"]
    stated_total: Optional[float]
    calculated_total: float
    line_items: List[LineItem]

    @field_validator('calculated_total')
    @classmethod
    def totals_must_match(cls, v, info):
        items = info.data.get('line_items', [])
        items_sum = sum(li.amount for li in items)
        if abs(v - items_sum) > 0.01:
            raise ValueError(
                f"calculated_total {v} != sum(line_items) {items_sum}"
            )
        stated = info.data.get('stated_total')
        if stated is not None and abs(stated - items_sum) > 0.01:
            raise ValueError(
                f"stated_total {stated} != sum(line_items) {items_sum}"
            )
        return v

# ---------- 2. JSON SCHEMA FOR TOOL_USE ----------
extract_tool = {
    "name": "extract_invoice",
    "description": "Extract structured data from an invoice",
    "input_schema": {
        "type": "object",
        "properties": {
            "vendor_name": {"type": "string"},
            "vendor_type": {
                "type": "string",
                "enum": ["supplier", "service", "other", "unclear"]
            },
            "vendor_type_other": {"type": ["string", "null"]},
            "currency": {
                "type": "string",
                "enum": ["USD", "EUR", "GBP", "unclear"]
            },
            "stated_total": {"type": ["number", "null"]},
            "calculated_total": {"type": "number"},
            "line_items": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "description": {"type": "string"},
                        "amount": {"type": "number"}
                    },
                    "required": ["description", "amount"]
                }
            }
        },
        "required": [
            "vendor_name", "vendor_type", "currency",
            "calculated_total", "line_items"
        ]
    }
}

# ---------- 3. PROMPT WITH CRITERIA + FEW-SHOT ----------
SYSTEM_PROMPT = """Extract structured data from invoices.

Rules:
- Extract amounts as numbers (not strings)
- Use "unclear" for currency only when no symbol/code present
- Return null for stated_total ONLY if no total in the document
- Do NOT fabricate values to fill required fields

Examples:

INPUT: "Acme Corp - 3 widgets @ $10 = $30, total $30 USD"
OUTPUT: vendor_name="Acme Corp", vendor_type="supplier",
  currency="USD", stated_total=30.00, calculated_total=30.00,
  line_items=[{"description": "3 widgets", "amount": 30.00}]
REASONING: Standard invoice; sum matches stated.

INPUT: "Quote from BetaServices for consulting work, no totals listed"
OUTPUT: vendor_name="BetaServices", vendor_type="service",
  currency="unclear", stated_total=null, calculated_total=0.00,
  line_items=[]
REASONING: Quote with no amounts. Returning null - don't fabricate.

INPUT: "Gamma LLC, services rendered, billing: 100 EUR"
OUTPUT: vendor_name="Gamma LLC", vendor_type="service",
  currency="EUR", stated_total=100.00, calculated_total=100.00,
  line_items=[{"description": "services rendered", "amount": 100.00}]
REASONING: Single line item; description from billing context.
"""

# ---------- 4. EXTRACTION WITH BOUNDED RETRY ----------
def extract(document: str, max_retries: int = 2):
    messages = [{
        "role": "user",
        "content": f"Extract from this invoice:\n\n{document}"
    }]

    for attempt in range(max_retries + 1):
        resp = client.messages.create(
            model="claude-sonnet-4-5",
            max_tokens=2048,
            system=SYSTEM_PROMPT,
            tools=[extract_tool],
            tool_choice={"type": "tool", "name": "extract_invoice"},
            messages=messages
        )
        raw = resp.content[0].input

        try:
            return ExtractionResult(**raw), attempt
        except ValidationError as e:
            if attempt == max_retries:
                return None, attempt
            messages.append({"role": "assistant", "content": resp.content})
            messages.append({
                "role": "user",
                "content": (
                    f"Validation failed: {e}\n\n"
                    f"Re-examine the document and produce a corrected "
                    f"extraction. If data is genuinely absent, return "
                    f"null rather than guessing."
                )
            })

# ---------- 5. RUN ON 10 DOCS AND LOG OUTCOMES ----------
def run_pipeline(documents):
    results = {"pass": 0, "retry_pass": 0, "human_review": 0}

    for i, doc in enumerate(documents):
        result, attempts = extract(doc)
        if result is None:
            results["human_review"] += 1
            print(f"Doc {i:02d}: HUMAN_REVIEW after {attempts} retries")
        elif attempts == 0:
            results["pass"] += 1
            print(f"Doc {i:02d}: PASS")
        else:
            results["retry_pass"] += 1
            print(f"Doc {i:02d}: PASSED on retry {attempts}")

    print(f"\nFinal: {results}")
    return results
