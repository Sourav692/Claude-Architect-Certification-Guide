Question 0101
Task 4.1FP trust

Your security review agent flags 200 issues per week. The "input validation" category has 22% precision; developers ignore that category and now also ignore the "auth" category (which has 88% precision). Which action first?

  • AAdd "only flag with high confidence" to the prompt.
  • BLower the temperature to 0.
  • CTemporarily disable the input-validation category, rewrite its criteria, then re-enable.
  • DAdd a confidence score field and filter to scores > 0.8.
Why C

High-FP categories poison trust in the accurate ones around them. The fix is disable-and-rewrite: protect developer trust in the working categories while you fix the broken one offline. A and D are vague-confidence theater — the model has no calibrated notion of confidence. B is unrelated; temperature controls sampling randomness, not what counts as a finding.

Question 0202
Task 4.3tool_choice

You have three extraction tools (invoice, receipt, purchase_order) and the document type is unknown. You need guaranteed structured output. What tool_choice?

  • A"auto"
  • B{"type": "any"}
  • C{"type": "tool", "name": "invoice"}
  • DOmit tool_choice entirely.
Why B

{"type": "any"} forces a tool call (so output is always structured) while letting Claude choose which extractor based on the document. A and D default to "auto" — Claude may return text. C locks to one extractor regardless of document type, which is wrong when the type is unknown.

Question 0303
Task 4.3fabrication

Your contract extractor's governing_law field returns "California" even for contracts with no governing-law clause. Schema marks the field required, type string. What's the fix?

  • AAdd a few-shot example showing the model to default to "California" when missing.
  • BMake the field nullable so the model can return null when the clause is absent.
  • CAdd a Pydantic validator that rejects "California".
  • DForce a retry until the model returns something different.
Why B

Required + non-nullable forces the model to fabricate to satisfy the schema. Nullable lets it correctly return null when the clause is absent. A teaches it to fabricate worse. C just rejects the symptom — model will pick another plausible default. D wastes calls on a problem the schema is causing.

Question 0404
Task 4.5API selection

You have two workflows: (a) PR-blocking pre-merge review, (b) nightly tech-debt scan. Manager wants both moved to the Message Batches API for 50% savings. What's correct?

  • AMove both — savings outweigh latency.
  • BMove only the nightly scan; keep PR review on sync.
  • CKeep both on sync — batch result ordering is unreliable.
  • DMove both, with a fallback to sync if a batch is slow.
Why B

Batch fits non-blocking, latency-tolerant workloads; sync fits blocking workflows where developers are waiting. The 24-hour batch ceiling makes batch unworkable for pre-merge. C reflects a misconception — custom_id handles correlation cleanly. D over-engineers; matching API to workflow is the simpler, correct answer.

Question 0505
Task 4.4retry boundary

Your invoice extractor sometimes fails validation: line_items.sum() != stated_total. About 60% of failures are model errors fixable on retry; the other 40% are documents where the line items are genuinely missing. What architecture?

  • ARetry indefinitely until validation passes.
  • BBounded retries (2-3) with the validation error appended; route remaining failures to human review.
  • CLower the model temperature to reduce the failure rate.
  • DRemove the line-items sum check and trust stated_total.
Why B

Bounded retry with error feedback for the fixable 60%; human routing for the unfixable 40% (data genuinely absent). A wastes cost on unfixable cases. C doesn't address what's wrong. D abandons the most valuable semantic check you have.

Question 0606
Task 4.6multi-pass

A 14-file PR review produces inconsistent depth, missed bugs, and contradictory findings (same pattern flagged in one file, approved in another). Best fix?

  • AUpgrade to a model with a 1M-token context window.
  • BRun three independent passes on the full PR; only flag issues appearing in ≥2 of 3.
  • CSplit into per-file passes for local issues + a separate integration pass for cross-file flow.
  • DRequire developers to split the PR into 3-4 file submissions.
Why C

Root cause is attention dilution across files. Per-file focused passes plus an integration pass solves it. A doesn't fix dilution — bigger context still spreads attention across files. B is crude consensus that misses unique findings and adds 3× cost. D shifts the architectural problem onto humans.

Question 0707
Task 4.3schema scope

Which set of failures does tool_use with a strict JSON schema eliminate?

  • AJSON syntax errors, missing required fields, wrong-type fields, invalid enums.
  • BAll semantic correctness errors.
  • CHallucinated values for required fields.
  • DLine items not summing to the stated total.
Why A

tool_use eliminates syntactic errors only. Semantic errors (B-D) survive — that's why Task 4.4 (validation-retry with semantic validators) exists. The most-tested confusion on this domain is conflating "schema-validated" with "correct."

Question 0808
Task 4.2format judgment

Your invoice extractor returns tax_amount: null on invoices that show tax as "VAT @ 20%" rather than a dollar amount. Schema is correct (nullable). What's the right fix?

  • AForce tax_amount to be required so the model has to produce a value.
  • BAdd 1-2 few-shot examples showing extraction from VAT-style invoices, with reasoning that converts the percentage to a dollar amount.
  • CSet tool_choice to "any" instead of forced.
  • DSwitch to the Message Batches API.
Why B

Few-shot teaches the judgment to convert percentage to dollar amount. The schema is fine (nullable allows correct null behavior); what's missing is the judgment that the data is there in a different form. A causes hallucination. C and D are unrelated to format judgment.

Build exercise · all 6 tasks

Production extraction tool with validation-retry.

Build an extraction tool that processes 10 documents end-to-end with all six Domain 4 concepts wired together. This is the canonical full-stack exercise — if you can ship this cleanly, you've operationalized the entire domain.

  1. JSON schema with required, optional, and nullable fields; an enum that includes "unclear" and "other" + detail string.
  2. 2-3 few-shot examples in the system prompt — at least one demonstrating null-return for missing data.
  3. tool_choice forced selection (single extractor, must run).
  4. Pydantic validation including a semantic check (calculated_total vs stated_total).
  5. Validation-retry loop, bounded at 2 retries, with the specific error appended to the retry message.
  6. Process 10 documents, log each outcome (pass / passed-on-retry / human-review).

Stretch goals. Add a detected_pattern field for FP analysis. Wrap the 10 docs in a batch submission with custom_id. Add a second independent reviewer instance that flags suspicious values with a confidence label, then route low-confidence to a needs_review queue.
