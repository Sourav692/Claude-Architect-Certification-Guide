4.1 Check questions 2 q
Q01 Task 4.1FP trust

Your security review agent has 70% precision overall, but the "code style" category has 35% precision and developers complain it's noisy. A teammate suggests adding "only flag style issues you're highly confident about." Will this fix it? What's the right move?

Model answer

No. "High confidence" is vague — the model has no calibrated notion of confidence. Two real fixes: (a) temporarily disable the style category to restore developer trust in the accurate categories, then (b) rewrite style criteria as a categorical inclusion/exclusion list (e.g., flag only naming that violates the documented convention; skip everything else).

Q02 Task 4.1severity drift

You're classifying support tickets as Critical/High/Medium/Low. The same ticket gets different severities on re-runs. What single change fixes this?

Model answer

Anchor each severity level to a concrete example ticket. The model needs reference points, not adjectives. Without anchors, it picks severity by vibes — and the same ticket gets a different label each time. Adjective-only severity scales never produce stable classification.

4.2 Check questions 2 q
Q03 Task 4.2format variation

Your invoice extractor handles standard PDFs perfectly but drops tax_amount as null when tax appears as "VAT @ 20%" instead of a dollar figure. Schema is already specified. What do you add?

Model answer

Add 1-2 few-shot examples showing extraction from VAT-style invoices, with reasoning that explicitly converts the percentage form into a dollar amount. Schema enforces format; few-shot teaches judgment on format variation. The schema alone can't tell the model how to do the conversion.

Q04 Task 4.2quantity

You're choosing between (a) 12 few-shot examples covering every variation you've seen, or (b) 3 examples carefully chosen to illustrate ambiguous cases. Which performs better and why?

Model answer

(b). Three well-chosen examples teach a generalizable judgment pattern. Twelve examples eat the context window, increase cost, and often hurt by overfitting the model to surface patterns in your examples. Past 4, marginal example value drops sharply.

4.3 Check questions 2 q
Q05 Task 4.3tool_choice

You have three extraction tools (invoice, receipt, contract) and the document type is unknown until Claude reads it. You need guaranteed structured output. Which tool_choice?

Model answer

tool_choice={"type": "any"}. It forces Claude to call one of the three tools (so output is structured) while letting Claude pick based on the document. "auto" allows text responses; forced selection on a specific tool would lock you to one extractor regardless of doc type.

Q06 Task 4.3fabrication

Your contract extractor returns governing_law: "California" for every contract — including ones where the clause is missing. Schema marks the field as required, type string. What's wrong and how do you fix it?

Model answer

The schema forces fabrication. Required + non-nullable means the model must produce some string, so it picks a plausible default. Fix: make governing_law nullable ("type": ["string", "null"]) so the model can return null when the clause is absent. Optionally add an "unclear" enum if you want to distinguish "missing" from "ambiguous."

Q07 Task 4.4retry boundary

Your contract extractor fails validation 8% of the time because effective_date doesn't parse as ISO 8601. Retries succeed on 95% of those. The remaining 5% are contracts where the date is genuinely not stated. What's the right architecture?

Model answer

Bounded retry with error feedback for the format issues, then route the remaining 5% to human review. Don't keep retrying — the data isn't there. Architecture: try → validate → retry-with-error → after 2-3 retries, mark the field null with a requires_human_review flag.

Q08 Task 4.4FP debugging

Why is a detected_pattern field on findings more valuable than a confidence_score for debugging false positives?

Model answer

detected_pattern lets you cluster dismissed findings: "all dismissed flags fire on Logger.debug() calls" → concrete prompt fix. confidence_score just tells you the model felt unsure — not what category of input triggered the failure. Pattern names enable systematic debugging; confidence scores don't.

Q09 Task 4.5API selection

You have two workflows: (a) PR-blocking automated code review, (b) overnight tech-debt scan. Manager says: "Switch both to batch for the 50% savings." What do you tell them?

Model answer

Move only the overnight scan to batch — that's a non-blocking, latency-tolerant workload, perfect fit. Keep PR review on the synchronous API: developers wait for the result, and the 24-hour batch window destroys the workflow. Match each workflow to its appropriate API.

Q10 Task 4.5failure handling

Your nightly batch of 5,000 invoices had 47 failures, all due to documents over the context limit. Fix it before tomorrow night.

Model answer

Identify the 47 failures by custom_id, chunk those documents (split into sections that fit context, extract each, merge), resubmit only those 47 as a fresh batch. Don't re-run all 5,000. Optionally add a pre-flight token-count check so oversized docs auto-chunk before the next nightly run.

Q11 Task 4.6self-review

Your code-generation agent produces a function. You add an instruction at the end of the same prompt: "Now review your work for bugs." Why does this rarely catch real issues?

Model answer

The model retains its reasoning context from generation. It already has a committed mental model of what the code does and why — it's biased toward confirming, not challenging, that model. An independent instance with no prior context evaluates the artifact fresh and is far more likely to surface subtle issues.

Q12 Task 4.6attention dilution

A 14-file PR review gives detailed feedback on 4 files, superficial on 10, and contradicts itself across files. Two suggestions: (a) upgrade to 1M-token context, (b) split into per-file passes plus an integration pass. Which fixes it?

Model answer

(b). Root cause = attention dilution across files in a single pass — a structural problem with how attention allocates, not a context-size problem. A bigger context window still gives every file diluted attention. Per-file passes give each file focused attention; the integration pass handles cross-file concerns separately.
