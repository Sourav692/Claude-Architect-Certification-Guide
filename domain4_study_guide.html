4.1
Task statement 4.1

Explicit criteria over vague confidence.

Categorical criteria are binary tests the model can answer the same way every time. Vague confidence instructions are theater — the model has no calibrated notion of "high confidence," so it invents one and the threshold drifts.

The false-positive trust problem.

A reviewer that flags 100 issues with 30 wrong doesn't just lose 30% of its accuracy — it loses the trust developers had in the other 70. High false-positive categories poison the categories around them. Once a developer starts dismissing one category, they stop reading the others too.

The counter-intuitive fix: temporarily disable the noisy category while you rewrite its criteria. Don't leave it on with vague hedge words — those aren't real levers. The disable-rewrite-re-enable cycle is the answer the exam tests, not "lower confidence threshold" or "be more conservative."

Anti-pattern
Vague confidence-based criteria

The model has no calibrated definition of "high confidence." It invents one each call. Output drifts; FP rate is unstable.

# Sounds reasonable, achieves nothing
prompt = """Review this code change.
Be conservative and only flag
high-confidence issues. Use your
judgment on severity."""
Production grade
Categorical inclusion + exclusion

Each criterion is a binary test. Severity is anchored to concrete code patterns. Output is verifiable.

# Each rule is checkable
prompt = """Flag a finding ONLY when:
- SQL: user input concatenated
  into query without parameter
- Auth: route missing auth check
  that similar routes have
- Null: .get() result deref'd
  without null check

Skip: style, naming, patterns
that match the file's existing
convention."""

Severity calibration with anchored examples.

"Critical / High / Medium / Low" without anchors means nothing — the model picks severity by vibes, and the same bug gets a different label across runs. Anchor each level to a concrete code snippet. Now the model has reference points instead of adjectives.

SeverityAnchored definitionConcrete example
Critical Exploitable by an external user with no auth db.query("... WHERE id=" + req.id)
High Exploitable by an authenticated user if (user.role == 'admin' || true)
Medium Requires unusual conditions to trigger race condition under high concurrency only
Low Code-quality only, no exploit path unused variable, dead branch
Figure 4.1 · Vague vs categorical criteria why vague prompts can't improve precision
The left column degrades silently — the model produces output but the precision changes between calls. The right column is auditable: a finding either matches a binary criterion or it doesn't.

Code example.

# WEAK — vague, confidence-based
weak_prompt = """
Review this code change. Be conservative and only flag
high-confidence issues. Rate severity from 1-5.
"""

# STRONG — categorical + anchored severity
strong_prompt = """
Review the diff. Flag findings ONLY when one of these is true:
  - SQL injection: user input concatenated into a SQL string
    without parameterization
  - Auth bypass: a route handler missing an auth check that
    similar routes in this file have
  - Null deref: a value returned from .get() or .find() is
    dereferenced without a null check

Do NOT flag: style issues, naming, code that follows
the existing pattern in the file.

Severity rules (anchored):
  - CRITICAL: exploitable by an external user with no auth
    Example: db.query("SELECT * FROM users WHERE id=" + req.id)
  - HIGH: exploitable by an authenticated user
    Example: if (user.role == 'admin' || true)
  - MEDIUM: requires unusual conditions to trigger
    Example: race condition under high concurrency only

For each finding return:
  location, issue_type, severity, suggested_fix
"""

Click each to expand
  • 01
    "Add 'be more conservative' to the prompt to reduce false positives."
    Vague language is not a real lever. The model has no calibrated notion of "conservative" — it improvises a threshold per call. Precision doesn't improve; it just becomes unmeasurable.
    Rewrite criteria as inclusion + exclusion lists. Anchor severity to concrete code examples. Make every flag verifiable.
    +
  • 02
    "Lower the temperature to reduce false positives."
    Temperature controls sampling randomness, not what the model considers a finding. A deterministic wrong answer is still wrong.
    Fix criteria, not sampling. Temperature is unrelated to precision.
    +
  • 03
    "Have the model self-report a confidence score and filter to >0.8."
    Self-reported confidence is theater unless calibrated against a labeled validation set. The model has no inherent calibration — its 0.9 might still be 60% correct in practice.
    Use categorical criteria as the gate. If you want confidence routing later, calibrate it against ground truth first (Task 4.6).
    +
  • 04
    "Leave the noisy category running while you tweak the prompt."
    A high-FP category in production poisons trust in the accurate categories. Developers who start ignoring one category begin ignoring others.
    Disable the category temporarily. Rewrite criteria. Validate offline. Re-enable only when FP rate is back below threshold.
    +
4.2
Task statement 4.2

Few-shot prompting for consistency.

The single most effective technique for output consistency when instructions alone aren't enough. Two to four worked examples — with reasoning — teach the model a generalizable judgment pattern, not a list of cases to match.

When to deploy.

Reach for few-shot when detailed instructions still produce drifting output. The tells: same field returned in different formats ("$1,200" vs 1200), hallucination on missing data, drift on borderline cases, empty/null on required fields the model could have extracted from non-standard phrasing.

Few-shot does not make the model memorize cases. It makes the model generalize the underlying judgment pattern. Two well-chosen examples covering ambiguous cases beat twenty that all look the same.

How to construct examples.

  • Cover ambiguous cases, not obvious ones. A clearly malicious SQL injection teaches nothing. A safe-vs-unsafe pair where the difference is parameterization — that's where judgment lives.
  • Show reasoning, not just the answer. Include a short rationale per example. The model picks up the decision pattern, not just the output shape.
  • Span the failure mode. If the model confuses inline citations with bibliography entries, show one of each. Examples should map to the failure surface, not to your most common case.
Figure 4.2 · When to deploy few-shot decision flow
Don't add few-shot speculatively. Run instructions-only against real data first; deploy examples only against the specific failure modes you observe.

Code example — medical dosage extraction.

The third example is the most important: it teaches the model to return null when info is absent rather than fabricate. This single example dramatically reduces hallucination on incomplete documents. 

extraction_prompt = """
Extract the dosage from medical records. Dosages may appear
as numeric values, ranges, or informal language.

Examples:

---
INPUT: "Patient takes 10mg lisinopril once daily."
OUTPUT: {
  "drug": "lisinopril",
  "amount_mg": 10,
  "frequency": "daily",
  "reasoning": "Standard format - dose explicit in mg"
}
---
INPUT: "Pt on a baby aspirin qd"
OUTPUT: {
  "drug": "aspirin",
  "amount_mg": 81,
  "frequency": "daily",
  "reasoning": "'baby aspirin' is the standard term for 81mg;
   'qd' is the medical abbreviation for once daily"
}
---
INPUT: "Started on metformin, titrating up"
OUTPUT: {
  "drug": "metformin",
  "amount_mg": null,
  "frequency": null,
  "reasoning": "Dose not stated. Returning null rather than
   guessing - titration implies dose is changing"
}
---

Now extract from this record:
{document}
"""

Anti-patterns & exam traps

Click each to expand
  • 01
    "More examples = better. Use 10-20 to maximize coverage."
    Diminishing returns kick in past 4. Past that, you're spending context window for marginal gain — sometimes negative gain when surface patterns in your examples bias the model.
    2-4 well-chosen examples covering distinct ambiguous cases. Quality over quantity, every time.
    +
  • 02
    "Examples should match the user's exact case for maximum relevance."
    That's the failure mode. Examples teach a generalizable judgment pattern. If your example is a duplicate of the user's case, the model learns to memorize, not generalize — and breaks on the next variant.
    Pick examples that span the failure surface. Different inputs, same judgment principle.
    +
  • 03
    "Use few-shot to enforce a strict JSON output format."
    Few-shot is for judgment. JSON format enforcement belongs in tool_use schemas (Task 4.3) — that's the only mechanism that actually guarantees schema compliance.
    Use few-shot for judgment on edge cases. Use tool_use for format guarantees.
    +
4.3
Task statement 4.3

Structured output via tool use.

tool_use with a JSON schema is the only mechanism that guarantees schema-compliant output. It eliminates JSON syntax errors, missing required fields, and bad types — but it does not eliminate semantic errors. Hold both ideas at once.

What tool_use eliminates — and what it doesn't.

The core trap on this task: assuming "schema-validated" means "correct." It doesn't. Schema validation is a syntactic guarantee. The line items might still not sum to the total. The vendor name might still land in the customer field. Semantic correctness is Task 4.4's problem.

Eliminated by tool_use
Syntactic errors disappear
  • JSON syntax errors
  • Missing required fields
  • Wrong type (string vs number)
  • Invalid enum values
NOT eliminated
Semantic errors survive
  • Line items don't sum to total
  • Value placed in wrong field
  • Hallucinated values for required fields
  • Calculations referencing wrong source

tool_choice modes — memorize this table.

tool_choice valueBehaviorWhen to use
"auto" Model MAY call a tool OR return conversational text Conversational agent that sometimes extracts
{"type":"any"} Model MUST call ONE of the provided tools (its choice) Multiple extractors, document type unknown
{"type":"tool", "name":"X"} Model MUST call this SPECIFIC named tool Single extractor that must run

Schema design patterns.

  • Pattern 1 — Nullable for missing data. Mark fields nullable when the source may not contain them. Required + non-nullable forces the model to fabricate values to satisfy the schema.
  • Pattern 2 — "unclear" enum value. Add "unclear" as a valid enum option so the model has somewhere to land for ambiguous cases. Otherwise it picks the least-wrong real category, silently corrupting your data.
  • Pattern 3 — "other" + detail string. Combine "other" enum with a free-text X_other sibling field for extensible categorization. New categories captured without a schema change.
Figure 4.3 · tool_choice modes three guarantees, three use cases
When you need guaranteed structured output and you have one extractor, force it by name. When you have multiple extractors and the model needs to pick, use "any". "auto" is for conversational flows — never for blind extraction pipelines.

Code example — invoice extractor with all three patterns.

import anthropic
client = anthropic.Anthropic()

extract_invoice = {
    "name": "extract_invoice",
    "description": "Extract structured fields from an invoice",
    "input_schema": {
        "type": "object",
        "properties": {
            "vendor_name": {"type": "string"},
            "total_amount": {
                "type": ["number", "null"]   # Pattern 1: nullable
            },
            "currency": {
                "type": "string",
                "enum": ["USD", "EUR", "GBP", "unclear"]  # Pattern 2: unclear
            },
            "payment_method": {
                "type": "string",
                "enum": ["card", "wire", "check", "ach", "other"]
            },
            "payment_method_other": {            # Pattern 3: other + detail
                "type": ["string", "null"],
                "description": "If payment_method is 'other', describe it"
            }
        },
        "required": ["vendor_name", "currency", "payment_method"]
        # total_amount NOT required - may be missing on quotes
    }
}

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    tools=[extract_invoice],
    tool_choice={"type": "tool", "name": "extract_invoice"},
    messages=[{"role": "user", "content": f"Extract:\n\n{document_text}"}]
)

# Output guaranteed to be schema-valid
extracted = response.content[0].input

Anti-patterns & exam traps

Click each to expand
  • 01
    "tool_use guarantees correct output."
    It guarantees schema-compliant output, not semantic correctness. Numbers can still be wrong, fields can still be swapped, line items can still fail to sum.
    Add Pydantic semantic validators (Task 4.4). Schema is necessary but not sufficient.
    +
  • 02
    "Use tool_choice 'auto' when you want flexibility."
    "auto" lets Claude return conversational text instead of calling the tool. If your downstream code parses tool_use output, this is silent failure.
    Use "any" or forced selection whenever you need parseable structured output.
    +
  • 03
    "Mark every field required so we never get nulls."
    Required + non-nullable forces fabrication. The model picks a plausible-looking value rather than violating the schema. Your "required field" is now silently hallucinated.
    Mark fields nullable when source data may not contain them. Let the model return null honestly.
    +
  • 04
    "Use a strict enum without 'other' for clean categorization."
    Brittle. The first new category that appears in production breaks the pipeline — or, worse, gets misclassified into the closest existing bucket without you knowing.
    Add "other" + a sibling detail string. New categories surface as data, not as crashes.
    +
4.4
Task statement 4.4

Validation, retry, and feedback loops.

Catch semantic errors at runtime with retry-with-error-feedback. Send the failed extraction and the specific validation error back to the model for self-correction. Recognize when retries are pointless — when the data isn't in the document, no number of retries makes it appear.

The retry-with-error-feedback pattern.

After tool_use returns, run a validator (Pydantic is standard). On failure, send a follow-up request that contains: the original document, the failed extraction, and the specific validation error. The model self-corrects. Bound the retry count (typically 2-3) and route persistent failures to human review.

Figure 4.4 · Validation-retry loop runtime semantic correction
The retry message includes the specific validator error — not "try again." The specificity is what enables self-correction. Bound retries; don't loop forever.

The effectiveness boundary.

This is the single most testable concept on this task. Retry helps when the information is in the document and the model produced it wrong. Retry does not help when the information is genuinely absent. Recognize the difference or you burn cost on unfixable retries.

Retry fixes
Format and structural errors
  • "$1,200" returned as string when number required
  • Vendor placed in customer field
  • line_items don't sum to stated_total
  • Missing required field that IS in the document
Retry can't fix
Information absent from source
  • Field truly missing from the document
  • Required external context never provided
  • Domain knowledge gap
  • Source document refers to another doc not given

Two production patterns the exam tests.

  • calculated_total vs stated_total. Have the model extract both the stated total and a calculated total (sum of line items). Flag disagreement. The model checking its own arithmetic surfaces semantic errors that schema validation can't.
  • detected_pattern field. When flagging an issue, have the model record which code pattern triggered the flag. When developers dismiss findings, you can analyze dismissals by pattern to find systematic FP sources. Confidence scores don't enable this; pattern names do.

Code example — Pydantic validator with semantic check.

from pydantic import BaseModel, ValidationError, field_validator
from typing import Optional, List

class LineItem(BaseModel):
    description: str
    amount: float

class Invoice(BaseModel):
    vendor: str
    line_items: List[LineItem]
    stated_total: float
    calculated_total: float   # model computes; we verify

    @field_validator('calculated_total')
    @classmethod
    def totals_must_match(cls, v, info):
        items_sum = sum(item.amount for item in info.data['line_items'])
        if abs(v - items_sum) > 0.01:
            raise ValueError(
                f"calculated_total ({v}) doesn't match sum "
                f"of line_items ({items_sum})"
            )
        return v

def extract_with_retry(document, max_retries=3):
    messages = [{"role": "user",
                 "content": f"Extract:\n\n{document}"}]

    for attempt in range(max_retries):
        response = client.messages.create(
            model="claude-sonnet-4-5",
            tools=[invoice_tool],
            tool_choice={"type": "tool", "name": "extract_invoice"},
            messages=messages,
            max_tokens=1024
        )
        raw = response.content[0].input

        try:
            return Invoice(**raw)
        except ValidationError as e:
            messages.append({"role": "assistant", "content": response.content})
            messages.append({
                "role": "user",
                "content": (
                    f"Validation failed:\n{e}\n\n"
                    f"Re-examine the document. If data is "
                    f"genuinely absent, return null rather than "
                    f"guessing."
                )
            })

    raise RuntimeError("Failed after retries - route to human")
!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Retry indefinitely until validation passes."
    Wastes cost on unfixable cases. If the data is absent, retry-loop will never converge — you'll just burn API calls.
    Bound retries (2-3). Route persistent failures to human review.
    +
  • 02
    "Schema validation is enough — semantic errors are rare."
    Schema validation catches syntax. Semantic errors (line items not summing, fields swapped, hallucinated values) are common and silent. Without semantic validators they reach production undetected.
    Add Pydantic validators with cross-field semantic checks. calculated_total vs stated_total is the canonical pattern.
    +
  • 03
    "Just send 'try again' on failure — the model will figure it out."
    Without the specific error, the model retries the same way. Specificity is what enables correction.
    Always include the original document, the failed extraction, AND the specific validation error message in the retry prompt.
    +
4.5
Task statement 4.5

Batch processing strategy.

The Message Batches API trades latency for cost. 50% cheaper, up to a 24-hour processing window, no latency SLA, no multi-turn tool calling within a single batch request. Match each workflow to the right API.

The decision rule.

One question decides everything: is anyone waiting on the response in real time? A developer blocked on PR review, a user waiting on a chat reply, a downstream pipeline step blocked on the output — all count. If yes, you need the synchronous API regardless of cost. Batch has up to a 24-hour processing ceiling and no latency SLA — it cannot serve blocking workflows.

Mental hook: who is staring at the screen? If someone is, sync. If not, batch is on the table — but only if your SLA window comfortably exceeds the 24-hour batch ceiling.

WorkflowAPIWhy
Pre-merge code reviewSyncDeveloper is blocked on result
Customer-facing chatSyncUser waits in real time
Pipeline step (next step needs it)SyncPipeline blocked downstream
Overnight tech-debt scanBatchPosts at 9 AM, nobody waiting
Weekly compliance auditBatchLong SLA, no real-time pressure
Bulk historical re-extractionBatchScript runs it, results read later
Figure 4.5 · Sync vs batch decision tree two questions, three answers
The single question: is anyone waiting in real time? If yes, use sync — even at 2× the cost — because batch has no latency SLA. Batch is correct only when nothing is blocked AND your SLA window comfortably exceeds 24 hours.

Hard constraints — memorize these.

  • 50% cost savings — the headline benefit.
  • Up to 24-hour processing window — "often faster" is not a guarantee. Don't design around it.
  • No multi-turn tool calling within a single batch request. This kills validation-retry loops inside the batch. You can extract via tool_use, but you can't retry-with-error inside the same batch request.
  • custom_id is your correlation key. Without it you cannot match responses to inputs. Don't rely on submission order.

SLA math the exam loves.

Batch can take up to 24 hours per request. It often returns sooner — but you cannot rely on that. So your SLA window dictates whether batch is even viable:

  • SLA ≤ 24h — batch is off the table entirely. A single batch could blow the SLA on its own.
  • SLA = 30h — minimum viable for batch. 24h ceiling + 6h queue cushion = submit at least every 6 hours.
  • SLA ≥ 48h — comfortable. Submit on any reasonable cadence; safety margin is built in.

Practical designs use 4-hour cadences for safety against batch slowness even when the SLA leaves more room.

Failure handling.

  • Identify failures by custom_id.
  • Diagnose: oversized? malformed? schema mismatch?
  • Modify (chunk oversized docs, fix schema mismatch).
  • Resubmit only the failures. Never re-run the whole batch.
# Submit batch of 100 doc extractions
batch_requests = [
    {
        "custom_id": f"doc_{doc.id}",            # YOUR correlation key
        "params": {
            "model": "claude-sonnet-4-5",
            "max_tokens": 1024,
            "tools": [extract_invoice],
            "tool_choice": {"type": "tool", "name": "extract_invoice"},
            "messages": [{"role": "user", "content": f"Extract:\n\n{doc.text}"}]
        }
    }
    for doc in documents
]

batch = client.messages.batches.create(requests=batch_requests)

# Poll for completion
while True:
    status = client.messages.batches.retrieve(batch.id)
    if status.processing_status == "ended":
        break
    time.sleep(60)

# Correlate via custom_id
results, failures = {}, []
for r in client.messages.batches.results(batch.id):
    if r.result.type == "succeeded":
        results[r.custom_id] = r.result.message
    else:
        failures.append(r.custom_id)

# Resubmit ONLY failures - chunk oversized docs first

Anti-patterns & exam traps

Click each to expand
  • 01
    "Switch all workflows to batch for the cost savings."
    Blocking workflows can't tolerate the 24-hour window. The savings are real for non-blocking work; they're crippling for anything a developer or user is waiting on.
    Match API to workflow latency tolerance. Sync for blocking, batch for non-blocking.
    +
  • 02
    "Run validation-retry loops inside a single batch request."
    Batch API doesn't support multi-turn tool calling within one request. Retry-on-failure is a separate, post-batch step.
    Extract in batch. Validate after results return. Retry failures in a follow-up sync call or a follow-up batch.
    +
  • 03
    "Add a real-time fallback if the batch is slow."
    Over-engineered. The right answer is matching each workflow to the right API up front. Fallback complexity is a sign of unclear requirements.
    Decide ONCE per workflow: sync or batch. Don't blend.
    +
  • 04
    "Re-run the whole batch when some docs fail."
    Wastes cost. The successful docs are already done.
    Identify failures by custom_id. Modify only those (chunk, fix schema). Resubmit only the failures.
    +
4.6
Task statement 4.6

Multi-instance and multi-pass review.

Self-review fails because the model retains its reasoning context. An independent instance with no prior context is a far better critic. Large reviews split into per-file local passes plus an integration pass to avoid attention dilution.

Why self-review doesn't work.

A single Claude instance retains the reasoning context from generation. Telling it "now check your work" in the same conversation rarely catches subtle issues — the model has already committed to its line of reasoning and tends to defend, not challenge, that commitment. Even extended thinking inside the same call shows the same limitation.

The fix: a second, independent Claude instance with no prior reasoning context evaluates the artifact fresh. Nothing to defend, no committed mental model — it sees the artifact for the first time.

Multi-pass for large reviews.

Single-pass review of a 14-file PR suffers from attention dilution. Detailed feedback on some files; superficial on others; obvious bugs missed; and contradictory findings — flag a pattern in file A, approve the same pattern in file B. Bigger context windows don't fix this; the dilution is structural.

Figure 4.6 · Multi-pass review architecture focused passes beat one pass
Per-file passes catch local bugs with full attention. The integration pass examines cross-file data flow without re-flagging local issues. Each pass owns one concern.

Confidence-based routing.

Have the reviewer instance self-report confidence per finding (or per field). Auto- accept high-confidence; route low-confidence to humans. Crucial: confidence scores must be calibrated against a labeled validation set before they're trusted as routing signal. Uncalibrated, the model's "high" might still be 60%.

Code example — independent reviewer + multi-pass.

# Stage 1: per-file review (independent instance per file)
def review_file(file_diff):
    return client.messages.create(
        model="claude-sonnet-4-5",
        max_tokens=2048,
        system="""You are a code reviewer focused on LOCAL issues
                  in this single file. Do not consider cross-file
                  interactions. Flag bugs, security, null derefs.
                  Skip style.""",
        messages=[{"role": "user", "content": file_diff}]
    )

per_file = [review_file(d) for d in pr.file_diffs]

# Stage 2: cross-file integration pass
integration = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=2048,
    system="""Review ONLY cross-file interactions: API contract
              changes, data flow between modules, breaking imports.
              Do NOT re-flag local issues.""",
    messages=[{"role": "user", "content": pr.full_diff}]
)

# Stage 3: independent reviewer of generated code
# (different conversation - no prior reasoning context)
independent = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=2048,
    system="""You have not seen this code before. Review for
              correctness and edge cases. Output each finding
              with a confidence: high | medium | low.""",
    messages=[{"role": "user", "content": f"Review:\n\n{generated_code}"}]
)

# Stage 4: confidence-based routing
for finding in parse(independent):
    if finding.confidence == "high":
        auto_apply(finding)
    else:
        route_to_human(finding)

Anti-patterns & exam traps

Click each to expand
  • 01
    "Tell the model to review its own work in the same conversation."
    The model retains its reasoning context. It already has a committed mental model and is biased toward confirming, not challenging, it. Subtle issues survive.
    Spawn an independent instance with no prior context. The fresh evaluator catches what the original missed.
    +
  • 02
    "Upgrade to a model with bigger context to fix attention dilution."
    Bigger context still gives every file diluted attention. The dilution is structural — too many concerns at once. A 1M-token model with 14 files gets the same diluted output, just with more available room.
    Split into per-file focused passes plus an integration pass. The architecture is the fix.
    +
  • 03
    "Run three full-PR passes and only flag findings appearing in 2+ of 3."
    Crude consensus. Misses findings unique to one pass and adds 3× cost without addressing the actual problem (attention dilution from breadth, not from sampling variance).
    Address breadth structurally: per-file plus integration. Save consensus voting for cases where the model is genuinely uncertain on a known issue.
    +
  • 04
    "Trust self-reported confidence scores for routing decisions."
    Uncalibrated confidence is just a number. The model's 0.9 might be 60% accurate in your domain. Routing on uncalibrated scores is theater.
    Calibrate against a labeled validation set first. Track accuracy by confidence bucket. Only then route on confidence.
    +
