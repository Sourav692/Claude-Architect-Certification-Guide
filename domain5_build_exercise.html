The setup

A research coordinator that almost works.

You're inheriting this scaffold from a colleague. They say it "mostly works in the happy path." Production told a different story — reports come back occasionally with missing sources, occasionally with phantom sources, and occasionally with two concurrent sessions that step on each other's case facts. Your job: find every flaw before reading the solution.

What this code is supposed to do

  • Coordinator receives a research topic from a user
  • Delegates in parallel to a web_search subagent and a docs subagent
  • Each subagent returns either findings or a structured error
  • Coordinator synthesizes a final report — well-supported claims, contested claims, coverage gaps
  • Persistent case facts (the topic, query ID) survive across turns

Domain V build exercise

Each flaw below maps to one task statement. The fix isn't always a one-liner — most are structural. Read every fix carefully; the exam tests these patterns directly.

01
Task 5.3 · Error propagation
Coordinator never acts on is_retryable.

The whole point of is_retryable is to let the coordinator decide retry vs skip. Look at what the coordinator actually does:

if result.status == "success": all_findings.extend(result.findings) else: coverage_gaps.append({...}) # <-- always treated as gap, never retried

A retryable timeout is recorded as a coverage gap and the report goes out missing data that was probably one retry away from being available. The flag travels through the system carrying useful information that nobody reads.

Fix
When result.is_retryable is true, retry the subagent (with exponential backoff, capped attempts) before annotating a coverage gap. Only fall through to the gap branch when the retry also fails or when is_retryable is false.
02
Task 5.3 · Access failure vs valid empty
No distinction between access failure and a valid empty result.

Imagine the docs subagent calls _call_docs_api, the call succeeds, and the API returns an empty list because nothing matched. The current code returns:

return SubagentResult(status="success", findings=[])

Now compare that with a docs source that's actually broken — maybe the API key was revoked but the call doesn't raise. Same shape on the wire. The coordinator can't tell "queried successfully, found nothing" from "query never reached the source" — both end up as "no findings, all good."

This is the classic Task 5.3 trap. Reports go out claiming "no relevant sources" when in reality the source was unreachable.

Fix
Add an explicit branch that distinguishes success-with-results, success-with-empty-findings, and access failure. The success + empty case should be annotated in the synthesis output — "queried but no matches found" is a real finding that stakeholders need to see, not a silent zero.
03
Task 5.6 · Information provenance
The Finding schema is missing collection_date and methodology.

Look at the dataclass:

@dataclass class Finding: claim: str source_name: str source_url: str publication_date: str # <-- when the source was published evidence_excerpt: str # Missing: collection_date (when the data was measured) # Missing: methodology (how the number was derived)

The synthesis logic needs to distinguish trends from conflicts. Two sources reporting different battery prices in different quarters are showing a trend; two sources from the same quarter with different methodologies are showing a real conflict.

With only publication_date, you'll mismatch these. A study collected in Q1 2024 but published in Q4 2024 looks contemporaneous with a Q4 2024 collection. Same publication month, totally different periods of measurement.

Fix
Add collection_date (when the data was measured) and methodology (how it was derived). Conflict detection should compare collection_date, not publication_date. Methodology lets the report explain why two sources disagree even on the same period (e.g., "IEA uses sales registrations; BNEF includes pre-orders").
04
Task 5.6 · Trend vs conflict
The trend / conflict logic in synthesize is naïve and inverted in one branch.

Look at the synthesis loop:

dates = {f.publication_date for f in findings} if len(dates) > 1: # Different dates → trend well_supported.append(...) else: # Same date → conflict contested.append(...)

Two problems hiding in plain sight:

  • It uses publication_date when the right field would be collection_date (see flaw #3).
  • The same date branch treats every cluster as contested. But two sources from the same date that agree on a number are well-supported, not contested. Conflict requires same period AND numeric divergence — agreement on the same date is the strongest possible signal.

Net effect: any topic where two sources happened to report on the same day appears contested in every report, even when both sources gave identical numbers. Stakeholders see false uncertainty everywhere.

Fix
Conflict requires (a) overlapping collection_date AND (b) numeric divergence beyond a tolerance (e.g., >15%). Same period + numeric agreement → well-supported. Different periods → trend. Same period + divergence → contested. Three branches, not two.
05
Task 5.1 · Context preservation
Case facts are a module-level global — concurrent calls clobber each other.

This is the most production-shaped flaw — invisible in single-threaded testing, catastrophic at scale:

case_facts = { "topic": None, "query_id": None, "started_at": None, } async def run_coordinator(topic, query_id): case_facts["topic"] = topic # <-- mutates global case_facts["query_id"] = query_id # <-- mutates global ...

Two coordinators handling two different research topics in the same process clobber each other's case facts. Coordinator A sets topic = "EV adoption", then a microsecond later Coordinator B sets topic = "solar pricing". When A's build_system_prompt() runs, it sees B's topic.

Persistence is real here, but isolation is broken. The data persists — across requests it shouldn't.

Fix
Make case facts a per-request object — pass it explicitly through the call graph, or scope it to the coordinator's lifetime. Either a dataclass instance per call, or a contextvar if you need ambient access. Never a module-level mutable dict.
Bonus flaw · not in the five

build_system_prompt() is constructed but never sent to the API.

Look at run_coordinator carefully — it calls build_system_prompt(), assigns the result to a local variable, and never uses it. The persistent case facts pattern from Task 5.1 only matters if those facts reach the model. In a real implementation, this string would be passed as the system parameter on every client.messages.create() call. Here, it's a no-op. Easy to miss; easy to ship.

The takeaway

None of these flaws are syntax errors. The code runs. The tests probably pass. Each flaw produces quietly wrong outputs — reports missing sources, conflicts where there's agreement, contaminated case facts under load — that look fine until a stakeholder asks where a number came from.

That's Domain V. Most of the failure modes don't crash. They just produce confidently wrong reports. Build the patterns in early; retrofitting them under fire is expensive.
