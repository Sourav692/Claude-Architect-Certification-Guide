05.1
Task statement 5.1 · Context preservation

Persistent facts. Outside summarized history.

On the exam: when an agent forgets numbers, dates, or order IDs across turns, the answer is a persistent case facts block, not a bigger context window. Bigger windows fix capacity. Case facts fix attention.

The three forces working against you

Every API call to Claude is stateless. Your application sends the entire conversation history each turn. As that history grows, three failure modes appear:

  • Progressive summarization. Condensing turns to save tokens loses the precise things — amounts, percentages, dates, order IDs, customer-stated expectations — and replaces them with vague language ("recent purchase", "defective item").
  • Lost-in-the-middle. Models reliably attend to the start and end of long inputs. Information buried in the middle of a 30-turn transcript may be omitted from reasoning even when present.
  • Tool result bloat. A single lookup_order call can return 40+ fields when only 5 matter. Across 10 lookups, the noise crowds out signal.
Figure 5.1 · The persistent case facts pattern
The case facts block is rebuilt into the system prompt every turn. Numbers cannot drift. The summarized history captures tone and intent — fine for narrative coherence, dangerous for transactional values. Two layers, two purposes.

The persistent case facts pattern in code

Extract structured facts the moment they appear. Inject them into every prompt as a separate, non-summarized block. Trim verbose tool results before they enter context — never let irrelevant fields accumulate.

# Persistent state — survives across turns, never summarized case_facts = { "customer_id": None, "order_id": None, "refund_amount": None, "purchase_date": None, "issue_type": None, } def trim_tool_result(raw, keep_fields): # Strip 40+ field tool output to only what matters return {k: raw[k] for k in keep_fields if k in raw} def build_prompt(user_message): system = f"""You are a returns agent. <case_facts> {json.dumps(case_facts, indent=2)} </case_facts> Treat case_facts as authoritative. If user contradicts, ask to confirm. """ messages = summarized_history + recent_turns + [ {"role": "user", "content": user_message} ] return system, messages # Trim BEFORE results enter context trimmed = trim_tool_result(raw_order, keep_fields=["id", "amount", "date", "status"]) case_facts["order_id"] = trimmed["id"]

Mitigating lost-in-the-middle

When you must include a long aggregated input — research findings, document analysis, multi-source synthesis — fight position bias with structure:

  • Place the key findings summary at the top of the input. Don't bury the conclusion in paragraph 12.
  • Use explicit section headers for detail blocks so the model can navigate.
  • For subagent outputs feeding a synthesis step, require structured records (claim + source + date) over verbose prose.

  • 01
    "Switch to a model with a larger context window."
    Bigger windows fix capacity, not attention quality. Lost-in-the-middle still bites at any size. The information is being de-prioritized, not truncated.
    Persistent case facts block. Trim verbose tool results. Place key findings at input boundaries, not the middle.
    +
  • 02
    "Summarize aggressively to save tokens."
    Summarization is lossy where it hurts most: numbers, dates, and customer-stated expectations get condensed into "the customer wants a refund for something defective". Catastrophic for transactional flows.
    Two-layer state: facts block (durable, structured) + summarized history (tone, intent). Numbers live in the facts block.
    +
  • 03
    "Trust the model to ignore irrelevant tool fields."
    Verbose tool output crowds the context. Across many calls, signal is buried under noise. The model can't selectively forget what's already in its window.
    Trim upstream. Wrap tools with field-selection logic, or use a PostToolUse hook to strip output before it enters conversation history.
    +
  • 04
    "Drop old turns when context fills up."
    Conversation coherence breaks. Subsequent API calls need the full history to maintain the thread. The fix isn't deletion; it's smarter persistence of what matters.
    Compress old turns into the summarized history layer. Keep recent turns verbatim. Keep facts in the durable block regardless.
    +
"What you fail to persist explicitly will be summarized away. What you fail to structure will be lost in the middle."

05.2
Task statement 5.2 · Escalation & ambiguity

Three valid triggers. Sentiment is not one.

On the exam: any answer involving sentiment-based escalation or self-reported model confidence is wrong. Reliable triggers are explicit human request, policy gap, or stalled progress — and you teach them with few-shot examples.

The three valid triggers

Memorize these. The exam will test all of them, and several distractors will dress up sentiment or self-rated confidence to look reasonable.

  • Customer explicitly requests a human. Escalate immediately. Don't first attempt investigation. Don't try to talk them out of it.
  • Policy gap or ambiguity. Policy is silent on the customer's specific request — competitor price match when policy only addresses own-site adjustments, refund window edge cases, etc. Don't make up policy. Escalate.
  • Inability to make meaningful progress. Agent has tried, has hit a wall. Not "this seems hard," but actual stalled progress.

The two unreliable proxies

These look reasonable in a system prompt. They produce bad outcomes in production.

Anti-pattern · Sentiment
"Customer seems frustrated → escalate."

Sentiment doesn't correlate with case complexity. A frustrated customer with a simple defective-item return doesn't need a human; they need their refund. Sentiment-based triggers cause over-escalation and waste reviewer capacity.

Anti-pattern · Self-confidence
"If model confidence < 7 → escalate."

LLMs are poorly calibrated on their own confidence. They output 9/10 for hallucinations and 4/10 for correct answers. Without calibration against labeled validation data, raw self-reports are noise.

Figure 5.2 · Escalation decision flow
Three paths to escalation (red), one to resolution (green), one to clarification (yellow). Sentiment is nowhere on this diagram. Frustration alone doesn't escalate — frustration plus an explicit human request does.

The frustration nuance

This is precisely worded in the skill statement and frequently tested:

Acknowledge frustration while offering resolution when the issue is within the agent's capability, escalating only if the customer reiterates their preference for a human.

So: frustration alone is not a trigger. Frustration plus an explicit human request is. Frustration with a straightforward in-scope problem? Acknowledge, resolve, move on.

Ambiguous customer matching

When get_customer(name="John Smith") returns three matches, the wrong reflex is to pick by heuristic — most recent order, highest LTV, alphabetical. The right reflex is to ask for an additional identifier: email, phone, order number.

# WRONG — heuristic selection def select_customer(matches): return max(matches, key=lambda c: c["last_order_date"]) # RIGHT — request clarification def handle_multiple_matches(matches): return { "action": "request_clarification", "message": ( f"I found {len(matches)} accounts under that name. " "Could you share your email or order number?" ), }

Few-shot escalation criteria in the system prompt

Prose like "be careful about escalating" produces inconsistent behavior. Concrete input/action examples let Claude generalize to novel cases.

SYSTEM_PROMPT = """You are a returns agent. <escalation_criteria> ESCALATE immediately when: 1. Customer explicitly requests a human ("transfer me", "I want a person") 2. Policy is silent or ambiguous on the customer's specific request 3. You cannot make meaningful progress after reasonable attempts DO NOT escalate based on: - Customer frustration alone - Your own uncertainty (use tools instead) - Case "feeling complex" </escalation_criteria> <examples> Example 1 — Resolve, do not escalate User: "Third time calling. Refund order #84221, screen broke." Action: Acknowledge frustration, run lookup_order, process_refund. Example 2 — Escalate immediately User: "Just give me a human, I don't want a bot." Action: escalate_to_human(reason="customer_request"). Example 3 — Escalate, policy gap User: "Match Amazon's price, it's $20 cheaper there." Action: escalate_to_human(reason="policy_gap_competitor_match"). Example 4 — Clarify, do not escalate Tool returned 3 customer matches for "John Smith". Action: Ask user for email or order number. </examples> """

Anti-patterns & exam traps

Click each to expand
  • 01
    "Have the agent self-rate 1–10 confidence and escalate below 7."
    Self-reported confidence is uncalibrated. The model assigns high scores to confident hallucinations and low scores to correct answers. The threshold becomes meaningless.
    Use explicit categorical criteria (human request, policy gap, no progress) rather than continuous self-rated confidence.
    +
  • 02
    "Run sentiment analysis and escalate negative sentiment."
    Sentiment doesn't track case complexity. Frustrated customers with simple problems just want their problem solved. Sentiment-based escalation increases queue load and decreases CSAT.
    Acknowledge frustration verbally, but resolve the case if it's in scope. Escalate only on explicit human request.
    +
  • 03
    "Train a separate classifier on historical tickets."
    Over-engineered for the symptom. The first-line fix is explicit criteria + few-shot examples in the system prompt — much lower-effort, much higher leverage. Save the classifier for after you've exhausted prompt fixes.
    Add explicit escalation criteria + 4–8 few-shot examples covering each trigger. Measure improvement before considering ML routing.
    +
  • 04
    "On multiple customer matches, pick the most recent."
    Heuristic selection on customer identity is dangerous. The wrong account gets the action. Refunds applied to wrong customers, orders shipped to wrong addresses.
    Ask the customer for an additional identifier — email, phone, order number — before proceeding with any action.

Task statement 5.3 · Error propagation

Structured context. Not silent suppression.

On the exam: the most-tested distinction is access failure vs valid empty result. They look identical ([]), they mean different things, and conflating them produces reports that confidently state "no findings" when the data source was actually broken.

The two anti-patterns dominating failed designs

  • Silent suppression. Subagent catches the error, returns []. Coordinator thinks the query succeeded with nothing to find. Synthesizes a report based on a lie.
  • Workflow termination. Subagent throws, coordinator crashes the whole pipeline. One flaky API takes down the entire research run.

The right answer is structured error context — the subagent tells the coordinator exactly what failed, what was tried, what partial results exist, and what alternatives might work.

Access failure vs valid empty result

Same shape on the wire. Different meaning. If your tool conflates them, the coordinator can't decide between retry, alternative, or skip.

Anti-pattern · Conflation
Both return {"results": []}

Web search timed out at 30s — wraps it as empty. Web search returned no matches for an obscure query — also returns empty. The coordinator can't tell broken from genuinely-no-data. Reports drift into confident wrongness.

Pattern · Distinguish
Access failure ≠ empty result

Timeout returns {status: "error", error_type: "timeout", is_retryable: true, ...}. Successful query with no matches returns {status: "success", results: []}. The coordinator can decide retry, alternative source, or annotate gap.

Figure 5.3 · Structured error propagation
Local recovery first — transient failures retry inside the subagent. Only unresolvable errors propagate up. Coverage gaps get annotated in the synthesis output rather than crashing the workflow.

The structured error schema

Every error a subagent propagates upward should carry this shape:

{ "status": "error", "error_type": "timeout", # transient | validation | permission | rate_limit "is_retryable": True, "attempted_query": "EV battery prices 2025", "attempts": 3, "partial_results": [ {"source": "ieee.org", "claim": "..."} ], "alternative_approaches": [ "try academic_db subagent", "narrow query to lithium-ion only" ], "human_message": "Web search timed out after 3 attempts." }

Compare to the anti-pattern:

# WRONG — generic, useless {"status": "error", "message": "search unavailable"}

The first lets the coordinator make a decision. The second leaves it guessing.

Local recovery before propagation

async def web_search_subagent(query): last_error = None for attempt in range(1, 4): # retry x3 try: results = await call_search_api(query) return SubagentResult( status="success", results=results, # may be [] — VALID empty attempted_query=query, ) except TimeoutError as e: last_error = e await asyncio.sleep(2 ** attempt) except PermissionError as e: # Not retryable — propagate immediately return SubagentResult( status="error", error_type="permission", is_retryable=False, attempted_query=query, ) # All retries exhausted — propagate with full context return SubagentResult( status="error", error_type="timeout", is_retryable=True, attempted_query=query, alternative_approaches=["academic_db", "narrower query"], )
!

Anti-patterns & exam traps

Click each to expand
  • 01
    "Catch all errors in subagent, return [] for clean coordinator handling."
    Silent suppression. Coordinator can't tell empty-because-broken from empty-because-no-matches. Worst case: report claims "no findings" when source was down.
    Distinguish access failures from valid empty results in the response shape. Status field plus error_type tells the coordinator what actually happened.
    +
  • 02
    "Terminate the entire workflow on any subagent failure."
    A single flaky external API kills the whole research run. Useful work from other subagents is discarded. Latency for partial-recovery scenarios skyrockets.
    Coordinator proceeds with what succeeded, annotates the report with explicit coverage gaps for failed sources.
    +
  • 03
    "Return generic error: search_failed to keep the interface simple."
    Hides the failure type. Coordinator can't decide retry vs alternative vs skip. Burns budget retrying permission errors that will never succeed.
    Structured fields: error_type (transient/validation/permission), is_retryable boolean, attempted_query, partial_results, alternative_approaches.
    +
  • 04
    "Retry forever in the coordinator until something works."
    Doesn't distinguish retryable from non-retryable errors. Permission errors and validation errors will never succeed on retry. You burn time and tokens.
    Coordinator inspects is_retryable. Retries only true cases. Permission/validation errors propagate as gaps.
    +
05.4
Task statement 5.4 · Codebase exploration

Subagents isolate noise. Scratchpads persist findings.

On the exam: when an agent in a long session starts saying things like "this codebase typically..." or "the class probably handles..." it's context degradation. The fix is structural — subagents, scratchpads, summary injection, /compact — never "bigger window."

The signature of context degradation

You're four hours into exploring a 200-file codebase. Hour one was great. By hour three, ask a specific question and you get answers like:

  • "Typically these systems use a service layer..."
  • "The RefundProcessor class probably handles..."
  • "Most codebases of this kind tend to..."

Notice the words: typically, probably, tend to. The model has read so much verbose discovery output that earlier specific findings are buried. It's pattern-matching to generic software knowledge instead of citing the actual class it examined two hours ago.

The four tools to fight degradation

ToolWhen to useWhat it does
Scratchpad filesLong sessions, findings worth keepingPersist findings to disk; reference in later prompts; survive context resets and crashes.
Subagent delegationVerbose discovery (find tests, trace deps)Isolate noise in a child context; main agent receives only a structured summary.
Summary injectionPhase transitionsCompress phase-1 findings into the start of phase-2 prompt; counters lost-in-the-middle.
/compactContext filling mid-sessionShrinks Claude Code's running context in place; preserves intent without restart.
Figure 5.4 · Subagent isolation with scratchpad
Each subagent does verbose grep/read work in its own context. Only short structured summaries flow back. The scratchpad persists findings across phase boundaries, /compact calls, and crashes — making the work durable.

Scratchpad files in practice

# Phase 1: Discovery — main agent spawns a subagent subagent_prompt = """ Search the codebase for all functions handling refunds. For each, return: file path, function name, one-line purpose. Output as a markdown list. Do not include source code. """ # Subagent does noisy grep/read work in isolation findings = run_subagent(prompt=subagent_prompt) # Main agent persists to scratchpad — durable across sessions with open("scratch/refund_entrypoints.md", "w") as f: f.write(f"# Refund Entrypoints — {datetime.now()}\n\n") f.write(findings) # Phase 2: Main agent injects scratchpad into next prompt phase2_prompt = f""" We previously catalogued refund entrypoints: {open("scratch/refund_entrypoints.md").read()} Now trace database writes triggered by each entrypoint. """

Crash recovery via state manifest

For long-running multi-agent jobs, periodically write a manifest. On crash, the coordinator reads the manifest and resumes without re-running completed phases.

manifest = { "session_id": "refund-investigation-2024-03-15", "phase": 2, "completed": ["entrypoint_discovery", "db_write_trace"], "pending": ["test_coverage", "cross_cutting"], "scratchpad_files": [ "scratch/refund_entrypoints.md", "scratch/db_writes.md", ], }

Anti-patterns & exam traps

Click each to expand
  • 01
    "Use a model with a larger context window."
    Bigger window doesn't fix attention degradation. Lost-in-the-middle still bites at any size. The signal is being de-prioritized, not truncated.
    Subagent isolation + scratchpad persistence + summary injection at phase boundaries.
    +
  • 02
    "Have main agent do all the file reading itself."
    Pollutes coordination context with raw file contents. This is exactly what causes degradation — the coordinator drowns in its own discovery output.
    Coordinator delegates verbose work to subagents. Subagents return structured summaries, not file dumps.
    +
  • 03
    "Restart from scratch when context degrades."
    Loses all progress. Hours of work discarded. The fix is to preserve what's valuable, not to throw it away.
    Scratchpad files + summary injection at phase transitions preserve findings. /compact compresses context in place.
    +
  • 04
    "Have subagents return full file contents to the main agent."
    Defeats the entire point of subagent isolation. Main agent gets flooded with raw output again — same problem as no subagents at all.
    Subagent contract: structured summary only. File path + symbol + one-line purpose. No source code in the return value.

Task statement 5.5 · Human review & confidence

Aggregate accuracy lies. Stratify before you trust.

On the exam: a 97% aggregate number can hide 70% accuracy on a critical field within a specific document type. The right answer always involves per-segment validation and stratified sampling — never trusting the average alone.

The trap in one paragraph

Your extraction pipeline reports 97% aggregate accuracy on a labeled validation set. Leadership wants to scale back human review. Three weeks after rollout, finance flags that invoice tax fields are wrong 30% of the time on European vendor docs — but customer name fields are 99.9% correct, and the average came out clean. The 97% number was real and useless.

Three concepts the exam will drill

  • Aggregate hides per-segment errors. Always validate by document type AND by field segment before reducing review.
  • Stratified random sampling. Sample within strata (doc type × vendor region × field × confidence band) to detect novel error patterns and measure error rates in supposedly-safe auto-processed extractions.
  • Field-level confidence scores, calibrated against labeled validation data, used to route review attention. Not the model's vibe — actual calibration.

Why raw self-confidence isn't enough

Same trap as Task 5.2: a raw model-emitted confidence score is uncalibrated. The model might output confidence: 0.95 for a hallucinated tax ID and confidence: 0.6 for a correctly extracted one. The score becomes useful only when you've calibrated it against a labeled validation set — measuring what 0.9 actually corresponds to in real accuracy terms.

Figure 5.5 · Confidence routing & stratified audit
Two paths into human review (yellow): low-confidence routing AND stratified sampling of high-confidence cases. The metrics block (orange) breaks accuracy down per type and per field, never aggregate. Recalibration loops back to update thresholds.

Different threshold per field

One uniform threshold is wrong. Money fields and free-text name fields have different error costs.

# Calibrated thresholds — derived from labeled validation set CONFIDENCE_THRESHOLDS = { "vendor_name": 0.85, # forgiving — name format is stable "invoice_total": 0.95, # strict — money matters "tax_amount": 0.95, # strict — money matters "invoice_date": 0.90, } def route_for_review(extraction, doc_type): # Route per FIELD, not per document fields_needing_review = [] for field, threshold in CONFIDENCE_THRESHOLDS.items(): conf = extraction.get(f"{field}_confidence", 0) if conf < threshold: fields_needing_review.append(field) if fields_needing_review: return f"human_review: {fields_needing_review}" return "auto_process"

Stratified sampling — why random isn't enough

Plain random sampling on 10,000 auto-processed extractions might miss systematic failures on rare document types. Stratify by:

  • Document type — invoice vs receipt vs contract
  • Vendor / source — US vendor vs EU vendor
  • Field type — date vs amount vs free text
  • Confidence band — 0.85–0.90 vs 0.90–0.95 vs 0.95+

Then sample within each stratum. Now you can detect: "high-confidence extractions are 99% accurate overall but 70% accurate on EU invoice tax fields." Aggregate sampling could not have surfaced that.

def stratified_audit_sample(auto_processed, sample_rate=0.02): # Sample 2% from each stratum so rare segments aren't missed strata = defaultdict(list) for record in auto_processed: band = "high" if record["min_confidence"] > 0.95 else "med" key = (record["doc_type"], record["vendor_region"], band) strata[key].append(record) audit_set = [] for key, records in strata.items(): n = max(1, int(len(records) * sample_rate)) audit_set.extend(random.sample(records, n)) return audit_set

Anti-patterns & exam traps

Click each to expand
  • 01
    "97% aggregate accuracy is excellent — automate the rest."
    Aggregate hides per-type and per-field failures. EU invoices might be 70% accurate inside that average. The error is concentrated, not distributed.
    Break down accuracy by document type AND by field. Verify no segment has materially lower accuracy before reducing review.
    +
  • 02
    "Use a single confidence threshold across all fields."
    Money fields and free-text fields have different error costs. A wrong tax_amount has bigger downstream impact than a slightly off vendor name.
    Per-field thresholds calibrated against labeled validation data. Stricter thresholds for high-cost fields.
    +
  • 03
    "Trust raw model self-confidence without calibration."
    Uncalibrated confidence is noise. The model assigns high confidence to fluent hallucinations. Without ground-truth calibration, the threshold means nothing.
    Calibrate against a labeled validation set. Measure: at what model-reported confidence does actual accuracy reach the target?
    +
  • 04
    "Random sampling of audited high-confidence extractions is sufficient."
    Random misses rare strata. A new document format that only appears in 2% of volume can have catastrophic accuracy without surfacing in random samples.
    Stratify by doc type, region, field, confidence band. Sample within each stratum. Track per-segment accuracy over time.

Task statement 5.6 · Information provenance

Claim-source mappings survive synthesis. Always.

On the exam: when sources disagree, the right answer is never "average them" or "pick the most recent." It's preserve all values with attribution and dates. Different dates plus different numbers usually means trend, not conflict.

The three things that go wrong in naïve synthesis

A multi-agent research system finds three sources discussing EV battery prices. Each cites a different number. The synthesis subagent receives all three, writes a polished report, and produces a single number — "$120/kWh" — with no attribution. Three things just went wrong:

  • Source attribution lost during synthesis. The claim-source mapping didn't survive the compression step. A stakeholder asks "where does that number come from?" and you have nothing.
  • Conflicting data silently resolved. The synthesis agent picked one value and dropped the others. No flag for the conflict. Stakeholders never see the disagreement.
  • Temporal context discarded. One source was Q1 2024, another Q3 2025. They weren't contradicting each other; they were measuring different points in time. Synthesis erased that distinction.

Trend vs conflict — the most testable distinction

Trend (different dates)
Battery prices, declining trend

$139/kWh — IEA, Mar 2024
$115/kWh — BNEF, Dec 2024
$108/kWh — Reuters, Sep 2025

Sources agree on direction. Range reflects measurement dates, not contested findings.

Conflict (same period)
Adoption rate, contested

18% YoY — IEA Outlook, 2025
31% YoY — BNEF Outlook, 2025

Same window, divergent numbers. Methodologies differ — IEA uses sales registrations, BNEF includes pre-orders. Real disagreement.

Figure 5.6 · Provenance-preserving synthesis
Subagents emit structured records (teal) — never plain prose. The synthesis agent's contract is to preserve those records through the merge. The final report is stratified by epistemic status: well-supported, contested, gaps. Stakeholders see the difference at a glance.

The required record shape

{ "claim": "EV battery pack prices reached $115/kWh", "source_url": "https://bnef.com/2024-battery-survey", "source_name": "BloombergNEF Battery Price Survey", "evidence_excerpt": "Pack prices fell to $115/kWh in 2024", "publication_date": "2024-12-10", "collection_date": "2024-Q4", "methodology": "weighted survey of 200+ packs" }

Conflict detection that respects time

def has_numeric_conflict(findings): # Conflict if numeric claims diverge AND collection dates overlap. # Different dates = trend, not conflict. nums = [(extract_number(f.claim), f.collection_date) for f in findings] nums = [(n, d) for n, d in nums if n is not None] if len(nums) < 2: return False same_period = all(d == nums[0][1] for _, d in nums) diverge = max(n for n, _ in nums) / min(n for n, _ in nums) > 1.15 return same_period and diverge

Anti-patterns & exam traps

Click each to expand
  • 01
    "When sources conflict, pick the most recent or most authoritative."
    Loses information. Stakeholders never see the disagreement. The picked source might not actually be most authoritative for that claim.
    Preserve all conflicting values with attribution. Structure the report to flag contested findings vs well-supported ones.
    +
  • 02
    "Average conflicting numbers for a single clean output."
    Hides disagreement. The average is itself a fabricated number that no source actually reported. Worse than picking one — actively misrepresents the data.
    Show all values with sources. Let the reader understand the spread and decide which methodology to trust.
    +
  • 03
    "Have synthesis write clean prose; trust it to keep sources accurate."
    Prose synthesis loses attribution silently. Sources get dropped during compression. No audit trail when stakeholders ask "where did this number come from?"
    Structured intermediate format. Subagent contract: emit records, not prose. Synthesis preserves source fields through the merge.
    +
  • 04
    "Different dates make sources unreliable — discard older ones."
    Conflates trend over time with source disagreement. A 2024 number and a 2025 number on a moving metric are showing change, not contradicting each other.
    Require publication_date and collection_date in every record. Conflict detection respects time. Trends get presented as trends.
    +
