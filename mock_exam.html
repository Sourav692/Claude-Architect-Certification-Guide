A 14-file PR review produces inconsistent depth, missed bugs, and contradictory findings (same pattern flagged in one file, approved in another). Best fix?

  • AUpgrade to a model with a 1M-token context window.
  • BRun three independent passes on the full PR; only flag issues appearing in ≥2 of 3.
  • CSplit into per-file passes for local issues + a separate integration pass for cross-file flow.
  • DRequire developers to split the PR into 3-4 file submissions.
Why C

Root cause is attention dilution across files. Per-file focused passes plus an integration pass solves it. A doesn't fix dilution — bigger context still spreads attention across files. B is crude consensus that misses unique findings and adds 3× cost. D shifts the architectural problem onto humans.

Question34
Domain 04 · Prompt Engineering & Structured Output Task 4.3schema scope

Which set of failures does tool_use with a strict JSON schema eliminate?

  • AJSON syntax errors, missing required fields, wrong-type fields, invalid enums.
  • BAll semantic correctness errors.
  • CHallucinated values for required fields.
  • DLine items not summing to the stated total.
Why A

tool_use eliminates syntactic errors only. Semantic errors (B-D) survive — that's why Task 4.4 (validation-retry with semantic validators) exists. The most-tested confusion on this domain is conflating "schema-validated" with "correct."

Question35
Domain 04 · Prompt Engineering & Structured Output Task 4.2format judgment

Your invoice extractor returns tax_amount: null on invoices that show tax as "VAT @ 20%" rather than a dollar amount. Schema is correct (nullable). What's the right fix?

  • AForce tax_amount to be required so the model has to produce a value.
  • BAdd 1-2 few-shot examples showing extraction from VAT-style invoices, with reasoning that converts the percentage to a dollar amount.
  • CSet tool_choice to "any" instead of forced.
  • DSwitch to the Message Batches API.
Why B

Few-shot teaches the judgment to convert percentage to dollar amount. The schema is fine (nullable allows correct null behavior); what's missing is the judgment that the data is there in a different form. A causes hallucination. C and D are unrelated to format judgment.

Question36
Domain 05 · Context Management & Reliability Task 5.1Multi-issue session

A support agent handles a session where the customer raises three separate order issues across 25 turns. By turn 22, the agent confuses order IDs, applies a refund amount from issue #1 to issue #3, and references "the order" without specifying which. What's the most effective architectural fix?

  • A
    Increase the API max_tokens so responses can be more detailed.
  • B
    Extract structured per-issue data (order ID, amount, status, customer-stated resolution) into a separate context layer keyed by issue, included in every prompt outside the summarized history.
  • C
    Force the agent to handle one issue at a time and end the session between issues.
  • D
    Have the agent re-summarize the whole session before every response.
Rationale · B is correct

Multi-issue sessions need structured issue data persisted as a separate context layer, keyed per issue. This prevents cross-contamination of order IDs and amounts. A is the capacity-not-attention trap. C creates artificial friction. D wastes tokens and still loses precision.

Question37
Domain 05 · Context Management & Reliability Task 5.2Escalation calibration

An agent escalates 42% of cases. Reviews show many escalations triggered by "customer used multiple exclamation marks — high frustration." Meanwhile, the agent autonomously attempts cases where policy is silent on the request (e.g., competitor price matching). First-contact resolution is 55%, target 80%. Best improvement?

  • A
    Add a finer-grained sentiment classifier to better distinguish real frustration from mild irritation.
  • B
    Have the agent self-report a 1–10 confidence score and escalate below 7.
  • C
    Replace sentiment-based escalation with explicit criteria (customer requests human, policy gap, no progress) plus 4–8 few-shot examples covering each trigger.
  • D
    Lower the escalation threshold and let the agent attempt every case.
Rationale · C is correct

Sentiment is an unreliable proxy. Self-reported confidence is uncalibrated. The right fix is explicit categorical criteria + few-shot examples targeting both ends of the calibration problem (over-escalation on frustration AND under-escalation on policy gaps). A doubles down on a broken proxy. B replaces one bad proxy with another. D removes the safety net entirely.

Question38
Domain 05 · Context Management & Reliability Task 5.3Empty vs broken

Your subagent calls a search API. Sometimes the call succeeds with no matches; sometimes the API is down; sometimes the credentials are revoked. Your current implementation returns {"results": []} uniformly on all failure modes plus on legitimate empty matches. What's the best redesign?

  • A
    Always raise an exception so the workflow halts.
  • B
    Add a single error string field; the coordinator checks if it's empty.
  • C
    Return structured results: explicit status ("success" / "error"), error_type, is_retryable, attempted_query, partial_results, alternative_approaches. Distinguish access failure from valid empty result.
  • D
    Hard-code a fallback dataset so empty results never reach the coordinator.
Rationale · C is correct

Structured error context is the explicit answer in this task statement. A terminates entire workflows on single failures. B isn't precise enough — coordinator still can't tell retryable from non-retryable. D fabricates data and hides real signal.

Domain 05 · Context Management & Reliability Task 5.3Recovery decision

A coordinator delegates to three subagents in parallel. One returns successfully. One returns a structured timeout with is_retryable: true and partial results. One returns a permission error with is_retryable: false. What's the right coordinator behavior?

  • A
    Terminate the entire workflow — partial completion is unacceptable.
  • B
    Use the successful result; retry the timeout (it's retryable); skip the permission error; synthesize with explicit coverage gaps for any source that ultimately can't be recovered.
  • C
    Retry all three until everything succeeds.
  • D
    Use only the successful result and silently drop the others from the final report.
Rationale · B is correct

The coordinator inspects is_retryable and acts accordingly: retry retryable, skip non-retryable, use what succeeded, annotate gaps in synthesis. A loses successful work. C burns budget on permission errors that won't succeed. D silently drops information that should be flagged as a coverage gap.

Question40
Domain 05 · Context Management & Reliability Task 5.4Architecture choice

A coordinator agent investigates a 200-file legacy codebase. It needs to: find all test files, trace the refund flow, identify external API dependencies. Each task involves reading dozens of files. What's the right architecture?

  • A
    Coordinator reads each file directly and keeps all contents in its context for cross-referencing.
  • B
    Spawn a subagent per investigation task; each reads files in its own context and returns a structured summary; coordinator persists summaries to scratchpad files and references them across phases.

    Run all three investigations in a single sequential conversation so context is shared.
  • D
    Use /compact after every file read to keep context small.
Rationale · B is correct

Subagent isolation keeps verbose discovery out of coordination context. Scratchpad files preserve findings across phase boundaries and crashes. A guarantees context degradation. C does the same in a single context. D is heavy-handed and loses signal alongside noise.

A multi-hour codebase exploration session crashes 75% through. The coordinator and three subagents had completed several investigation phases. What design decision would have made recovery clean?

Rationale · A is correct

Question42
Domain 05 · Context Management & Reliability Task 5.5Ongoing audit

Your team has been auto-processing high-confidence extractions for six months. Volume is 50,000/month. What ongoing audit pattern reliably catches novel error patterns introduced by document-format changes?

  • A
    Re-run the original validation set quarterly and report aggregate accuracy.
  • B
    Random sampling of 1% of auto-processed extractions for human audit.
  • C
    Stratified random sampling across document type, vendor region, and confidence band; track accuracy per stratum and per field over time.
  • D
    Increase confidence thresholds when complaints come in from downstream consumers.
Rationale · C is correct

Stratified sampling surfaces concentrated errors in rare strata. Random sampling misses them. Aggregate validation hides per-segment failures. Reactive threshold-tuning waits until users complain — too late.

Domain 05 · Context Management & Reliability Task 5.5Threshold design

Your extraction system outputs vendor_name, invoice_total, tax_amount, and invoice_date. You want to route low-confidence extractions to humans. What's the right threshold strategy?

  • A
    Use one uniform threshold (e.g., 0.9) across all fields for simplicity.
  • B
    Set per-field thresholds calibrated against labeled validation data — stricter on money fields (e.g., 0.95) than on free-text fields (e.g., 0.85) because error costs differ.
  • C
    Skip thresholds entirely; route every extraction to human review.
  • D
    Have the model self-rate on a 1–10 scale and route below 7.
Rationale · B is correct

Per-field thresholds calibrated against labeled validation data align review intensity with error cost. A treats high-cost fields too leniently and low-cost fields too strictly. C defeats the purpose of automation. D uses uncalibrated self-confidence.

Domain 05 · Context Management & Reliability Task 5.6Conflict handling

A multi-agent research system finds two credible sources reporting EV adoption rates for 2025 — IEA reports 18% YoY growth (using sales registrations); BNEF reports 31% YoY growth (including pre-orders). The synthesis subagent currently picks 18% as "more conservative" and drops 31%. Critique?

  • A
    Correct — when sources disagree, picking the more conservative estimate is safest.

    Should average them: (18 + 31) / 2 = 24.5%.
  • C
    Wrong. Both sources should be preserved with attribution and methodology notes; report should flag this as a contested finding so stakeholders see the disagreement.

    Discard both since they contradict.
Rationale · C is correct

Same time period + different methodology = real conflict. Preserve both with source attribution and methodology, present as contested. A loses information by editorial choice. B fabricates a number no source reported. D throws away signal.
